《修改代码的艺术》书评：常数，不是变量

2026-09-01T14:30:00.000Z2026-09-05T02:48:24.782ZChina

前言

这本书我在 2012 年刚入行时就见过推荐，但当时一门心思扑在 Bob 大叔那套，还有《深入分析 Java Web 技术内幕》这种更贴合当时处境的书上，硬是把它放过了。

现在回头看，放过它几乎是必然的——那会儿我在小企业，做的都是几个月就交付的项目，做完就翻篇，从没有机会维护一个长期产品。而一本教你”怎么在不动摇地基的前提下改造遗留系统”的书，对这样处境下的人，天然没有现实感。你看它，就像看一本讲怎么修古建筑的书——楼都没打算住过夜，谈何修缮。

直到 AI 时代，看《极客时间》那门「CC 企业级老项目改造实战」，专栏里对它的推崇让我重新把它从故纸堆里捞了出来——大量淘沙之下，这本老书居然焕发了第二春。专栏里对 seam 和特征测试的介绍，尤其是后者，给了我一个此前从没想到的角度。于是买回一本，用早起的那几十分钟，一天一天把它读完了。

先交代一个容易记错的事实：我脑子里一直记的是”07 年就成书了”，后来才确认——2007 年是中文版引进的时间，原版 Working Effectively with Legacy Code 早在 2004 年就出版了。也就是说，这事比你以为的还早了三年。

在行业里待了十几年，读这本书的大部分内容，我都觉得”融化在了血液里”。但也恰恰是那几个让我感到例外的点，让我重新审视了一件事：我这些年当成”新大陆”在部门里推的东西，人家二十年前就写成了书。一开始觉得”太搞笑了”，转念一想，能在还没遇到这本书的前提下、就在第一线摸到同样的结论，恰恰说明我踩在了真实的土地上。

1. 时滞：软件交付的常数

书里第一个击中我的名词，是 “时滞“——从做出修改，到得到反馈，中间经历的那段时间。

这个词，我一直在部门里用另一套说法在讲：快速反馈、微反馈环。但多知道一个专有名词，不是多了一条知识，而是多了一个锚点，让我能从另一个角度重新讲给团队听。

把”时滞”放到更大的坐标里看，会发现它根本不是 Feathers 一个人的发明，而是整个现代软件交付的第一性原理：TDD 的红-绿-重构、CI/CD 的分钟级流水线、DORA 指标里的变更前置时间、可观测性对 MTTR 的压缩——全部是在干同一件事：缩短”改代码 → 得反馈”的物理距离。

“时滞”是 legacy code 改造的地基，也是所有交付方法论共同的地基。

我过去把”微反馈环”当成一条团队管理经验在推，现在才意识到，它其实是条常数。多这层认知，推起来腰杆更硬。

2. 推迟决定：弹性从哪来

读这本书的过程里，我时不时会想起 SICP 里教授们那句影响了我的话：**”推迟做出决定的时机，这样你的系统就能充满弹性，能够更好应对变化。”**

这本书给我的整体感觉，正是这句话的工程化落地。测试，本质上是给系统的变更提前做出要求；而 seam、依赖注入、提取接口这一整套手法，本质上是把”依赖谁、绑定什么”的决定尽量往后推，好让测试到来的时候，系统还有腾挪空间去调整。

想明白这一点，我才把两个东西串成了完整的一句话：

“推迟决定”和”快速反馈”是一体两面，凑齐了才叫弹性。

  1. 只推迟、不反馈，是过度设计——那些为”未来可能需要”预留的抽象，十个有九个一辈子用不上；
  2. 只反馈、不推迟，是改一行崩一片——没有 seam 的系统，测试根本插不进去。

Feathers 和 SICP 在讲同一件事，只是一个是操作手册，一个是哲学纲领。

3. 项目还是产品：对时间轴的臣服

“你们做的是产品，不是项目”——这句话我最近一年反复强调。但细想，我前半段职业生涯恰恰活在相反的环境里：小企业、短周期、交付即终结。那种环境会天然把人塑造成”项目思维”，因为真的没有东西需要你维护。我如今强调”产品思维”，与其说是突然开窍，不如说是处境先变了，认知才追上来。

而这本书最让我敬佩的，恰恰是它对这件事的态度：它没有一句抱怨。

大多数团队面对 legacy code 的第一反应，是”要是当初架构设计对就好了”，然后幻想一次干净的重写。Feathers 不这么干。他默认代码就是会活很久、会持续收利息或付代价，然后直接上手，教你在飞行中换引擎。

抱怨”假如重来会如何”，是对”产品”这个事实最体面的逃避。

“重写”之所以诱人，正是因为它是逃离”产品”的借口——把持续决策的负担，一次性外包给一个想象中的全新开始。而这本书示范的，是臣服于时间轴，但不躺平。

4. 面向对象为什么赢了

书里对面向对象的反复推荐，放在今天看别有一番意味。

我们这行一直有一种叙事：面向对象最终发展壮大，是因为它”更符合人对世界的直觉建模”。但我读完这本书，得出一个更朴素的解释——是”可测试性”这个工程需求，反向把面向对象抬上了王座。

继承给你”子类化并覆写方法”的替换点，接口给你”提取抽象”的替换点，多态给你”运行时才绑定”的替换点。这三样，恰好都是制造 seam 最趁手的工具。Feathers 推崇的从来不是 OO 哲学，而是 OO 提供的可替换点。

语言范式的胜利，从来不是靠理论优雅，而是靠它能不能被方便地改造、被方便地测试。

面向对象不是瞬间发生的胜利，它是在”代码要活很久、还要能被安全地改”这个硬约束的持续筛选下，一步步胜出的。

5. 沙漠与绿洲：从童子军法则到良性循环

书里还有一句话，读到时让我停下来想了一会儿：

既有代码像是一片沙漠，你做的每次修改，应该是在其中开辟一块绿洲。当你把它们连成片的时候，过程中也就越来越有信心，进入良性循环。

这句话让我想起 Bob 大叔在《Clean Code》里那个著名的童子军法则——“让你离开时的营地，比你来时更干净”。两者说的是同一件事：渐进式地、不留烂摊子地改造。但我得承认，我更喜欢绿洲这个说法。

为什么？因为童子军法则是防守性的。它默认你的责任是”别把世界弄得更糟”——来的时候什么样，走的时候至少别更差。这是一种克制、一条底线，但它的情感底色，是负罪感的预防：你之所以要收拾，是因为怕亏欠。

而绿洲是进攻性的。沙漠不会因为”你没把它弄得更脏”而变好，它只会继续吞噬一切。可当你种下一块绿洲，你是真的在往沙漠里注入生机。区别不在动作，在方向：一个在”少破坏”，一个在”多创造”。

更妙的是那句”连成片”。单块绿洲是脆弱的，孤零零落在沙海里，随时可能被重新吞没；但绿洲一旦连成片，就会互相滋养——水分、阴凉、生态，都开始自我维持。这时改造就从一个”需要咬牙坚持的苦差”，变成了一个”越走越有劲的正反馈”。你改得越多，越有信心；越有信心，改得越顺。

童子军法则问的是”我有没有亏欠”，绿洲问的是”我有没有让它变好”。前者的终点是问心无愧，后者的终点是良性循环。

这也就解释了，为什么我这些年推的东西，兜兜转转都落在”反馈”二字上——时滞、微反馈环、绿洲连成片，讲的其实是同一件事：让每一次修改，都成为下一次修改的养料，而不是负债。

后记

合上书，最大的感受不是”学到了什么新东西”，而是一种被验证的踏实。

我一度觉得自己做的事毫无技术含量，都被前人实践过了。现在回头看，准确地说，我不是没读过书——这些年看的书不少，只是书里读到的那些东西，往往要隔上很多年，才在第一线被实践一一证实。说欣慰，是它们果然没错；说感慨，是证实来得太晚，而中间隔着的那些年，正是我的境遇本身。真正该自嘲的，是那些二十多年了还在把银弹当新大陆、还在幻想”重写一遍”就能抹掉债务的人。

最后，回到我最初想给这篇书评下的那个副标题——“常数，不是变量“。

这本书 2004 年就写完了，二十多年过去，里面的道理一点没旧，原因正在于此。它教的不是技术——技术是变量：2004 年的 JUnit、Ant、Struts，今天早换了好几茬，会迭代、会淘汰、会过时。它教的是常数：改一行代码要等多久才知道对错（时滞）、代码耦合越深越难动、没有测试的代码改起来像走夜路——这些 2004 年成立，2026 年一模一样，一点没差。

技术是变量，会过时；规律是常数，不会变。

这大概就是一本 04 年的老书，能在 AI 时代焕发第二春的真正原因：AI 改变了写代码的方式，却没改变”代码要活很久、还要能被安全地改”这个硬约束。老书的工具会过时，但它背后的常数，一直都在那里。

封面解读

这张封面是一幅关于”复活”的视觉隐喻，压缩了全文的核心命题。

那本泛黄风化的旧书 = 2004 年出版的《修改代码的艺术》，也是 legacy code 本身。 开裂的书脊、泛黄的书页，是时间的沉淀——它早被写成了书，也早被一代人实践过，只是长期躺在书架与认知的暗处。

封面肌理里隐约的电路纹路 = 代码与书的同构。 书和 legacy code 合为一体：代码不是印在纸上，而是”长”进了书的皮肤。它提醒你，这本书讨论的不是抽象理论，而是活生生的、正在腐烂的代码。

左上角那道青白色的光束 = 新处境照进来的光。 它没有照亮整个房间，只精准地落在这本书上，象征 AI 时代的老项目改造让这本书重新获得现实意义——不是书变了，是光的方向变了。

光尘粒子像余烬般浮起 = “焕发第二春”的具象化。 尘埃本是衰败的意象，但被光照亮后，它们成了向上浮起的余烬，暗示旧物在新的光照下重获生机。

一句话总结：暗处的老书被一束新时代的光点亮，正如二十年前的 legacy 方法论在 AI 时代重获现实意义——书没变，是处境变了。

原始素材和基础语料（人工）

我最近刚看完了一本很久之前的经典《修改代码的艺术》，其实这本书在我12年刚入行的时候就看到过推荐，虽然我看了bob大叔的一系列书籍，但确实放过了这本书。但Ai时代的到来，在看了《极客时间 - CC企业级老项目改造实战》之后，其中对于这本书的推崇，大量淘沙之下，这本书居然焕发第二春。尤其是专栏里对于 seam和特征测试，主要是后者的介绍，确实给了我一个未曾想到的角度，于是买了一本回来，用早起的几十分钟，逐步把它读完了。

不得不说在这个行业里待了这么多年，也不敢懈怠，大部分内容基本都属于融化在了血液里，并不让我感到意外。但也不是完全没有例外，其中发现的例外情况，更让我觉得自己做的事情没啥技术，都被前人实践过了这么多年07年时候都成书了，26年了你还拿这当新大陆，觉得自己在搞技术，太搞笑了。

第一个名词就是 时滞 —— 从做出修改到得到反馈经历的时间，这也是我一直在部门里强调的快速反馈，微反馈环的概念，但我觉得多知道一个专门这样的名词，能够更佳从不同角度强化。看这本书的过程中，我时不时会想起SICP这本影响我很深的书里，教授们的那句”推迟做出决定的时机，这样你的系统就能充满弹性，能够更好应对变化”，这整本书给我的感觉也是这样。

第三就是项目和产品的区别，这是我最近一年一直强调的，你们做的是产品，当下做的决定会持续影响之后，而这本书里的方法就是在应对这个之后，而不是抱怨，假如从新来可以如何如何；另外一点就是书中对于面向对象的反复推荐，所以面向对象最终发展壮大，不是瞬间发生的。

补充：一门心思扑在 Bob 大叔那套，还有诸如《深入分析 Java Web 技术内幕》这种更贴合自身实际的实际上——小企业，做的都是几个月就交付的项目，没机会维护长期产品。

补充：书里一句话——既有代码像是一个沙漠，你做的每次修改应该是在其中开辟一块绿洲，当你把它们连成片的时候，过程中也就越来越有信心，进入良性循环。这和 Bob 大叔 Clean Code 里的童子军法则如出一辙，但我似乎更喜欢这个说法。
