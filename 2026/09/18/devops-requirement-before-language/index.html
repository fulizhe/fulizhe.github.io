先有需求，才有软件

2026-09-18T14:11:35.000Z2026-09-19T09:35:29.607ZChina

前言

公司战略转向出海，于是第一次要做产品级的开源许可合规分析。这件事在过往完全不在考虑范围内。

要分析的制品包解开接近 4G，多年迭代，横跨 Vue、C++、Python、Go、Java 五个语言体系。领导给的窗口是一到两周。

我先把 Java 侧跑通了：扫描打通，报告出得来，证据链立得住。按计划，下一步是把这套已经验证过的流程推广到 JS 和 Go 两侧——不是甩一份需求过去，是带着跑通的方案去落地。

去之前我做过功课，技术栈和基本流程都和 AI 过了一遍。所以我不是空着手去的。

然后我收到了同一个回答：

我们这里面没有这些东西。

接下来是来来回回地解释。一轮，两轮，三轮。解释到某一轮，一句话从记忆深处被逼了出来——

先有需求，然后才有这个软件。别搞反了。

我越想越觉得，这句话不该由我来说。因为它太老了。老到它被写进每一本讲需求工程的书的第一章，老到我说出口的时候都觉得像在念课文。

可它偏偏是在那个场合、被”来来回回解释”逼出来的。这才是我要写这篇的原因。

1. 这句话不是我原创

Fred Brooks 1986 年写过一篇《No Silver Bullet》，第二年重印在 IEEE Computer 上（原文）。有名的是那句”软件工程没有银弹”。但同篇里有更基础的一段——他借亚里士多德，把软件的困难切成两类：

Following Aristotle, I divide them into essence, the difficulties inherent in the nature of software, and accidents, those difficulties that today attend its production but are not inherent.

本质（essence）是软件要做什么；附属（accidents）是它用什么去做。

紧接着他给了摘要里的第一句：

Fashioning complex conceptual constructs is the essence; accidental tasks arise in representing the constructs in language.

构建复杂的概念结构是本质；而附属的任务，产生于”用语言去表示这些概念”。

以及这句——我认为是整篇里最锋利的一句，也是这篇想钉住的那根钉子：

This essence is abstract in that such a conceptual construct is the same under many different representations.

——同一个概念结构，在很多不同的表示之下，是同一个东西。

那么请问，Java、Go、JavaScript 是什么？

它们是”表示”。是 representation。是 Brooks 在 1986 年就归进”附属”那一栏的东西。

所以这句话真的不是我原创。四十年前就写清楚了：需求是本质，语言只是表示。表示可以换，本质不换。

那我为什么会忘？我后来想明白了：不是忘了，是没在这个场合被激活。”知道一句话”和”用得上这句话”，中间隔着一整个现场。

2. 一个动作：把语言抠出去

道理知道了没用，得有动作。我给自己提炼了一个，只有一个动作：

把技术名词从句子里抠掉，看这句话还站不站得住。

站得住，它是需求；塌了，它是你的工具箱在说话。

“开源许可合规检查“——抠掉语言，剩下的是：检查一个软件里用了哪些第三方开源组件、每个组件什么许可、要履行什么义务、证据在哪。抠完，句子完好无损。这是一个完完整整、与实现无关的问题。

“设计模式“——抠掉语言：塌了。Java 里 GoF 那 23 个模式，搬到 Go 里就散架——Go 讲组合不搞继承，工厂那一套换成 functional options；再挪到 JavaScript，又是一堆函数式写法。设计模式的本体就是”某种语言里该怎么写”，抠掉语言，什么都不剩。

所以当对方把这两件事放进同一个抽屉——“设计模式在 Java 里用得多，合规八成也是 Java 的事”——那不是观点分歧，那是把附属当成了本质。

说得再狠一点：设计模式是”怎么写”，合规是”必须做”。前者随语言变，后者不随语言变。

3. “我们这里没有”——这句话缺了宾语

回到那句”我们这里面没有这些东西”。

它的问题不在态度，在语法：它缺宾语。

把这半句话补完，三种补法，三种结局。

补一：没有这个需求。

那就等于说：客户尽调的时候，因为我们用 Go，所以免检；投资方审计的时候，因为我们用 JavaScript，所以网开一面；上游厂商追责的时候，因为我们用 C++，所以放弃。

不会。法律不看编译器。

补二：没有这个工具。

这是一个事实层面的断言，可以当场验证。而验证结果不太好看：

  • Go 侧有 Google 官方的 go-licenses，一条 go-licenses check ./... --allowed_licenses=... 就能走完整个模块图（含传递依赖），命中不允许的许可直接返回非零；
  • npm 侧有 license-checker；
  • SBOM 生成工具 SPDX SBOM Generator 官方支持列表里，Maven、NPM、Yarn、GoMod、Cargo、PIP、Pipenv、Composer、DotNet、Gems、Swift 一个不缺。

“我们没有工具”这句话，在任何一个语言生态里都查得出反例。这不是观点分歧，是事实错误。

补三：没有做过。

这一条是真的。也是三条里唯一可以被解决的那一条。

但”没做过”和”不存在”，是两件事。

我怀疑很多句”我们这里面没有”的真实含义，其实是第三种被误报成了第二种——把”我没见过”，说成了”世上没有”。

经验的边界，被当成了世界的边界。

这不是笨，这是省力。承认”只是我没做过”，就得去学；说”世上没有”，就可以不动。同样一个陈述句，两种代价。

4. 合规不是技术属性，是法律属性

有人会退一步说：那至少得承认，不同语言里做法不一样吧？

做法不一样，没错。但”做法不一样”和”这事不存在”之间，隔着一整套国际标准。

先看最权威的那一份：ISO/IEC 5230，由 OpenChain 项目维护，是开源许可合规的国际标准（标准说明）。它规定的内容是这些：开源政策、程序角色与职责、人员能力、外部询问的受理渠道、组件的跟踪与管理流程、合规制品的归档、治理机构的设置。

通篇没有一个字提到编程语言。

不是漏了，是不需要。这个标准的定位写得很清楚：non-prescriptive——不规定你用哪个工具、走哪条技术路径，只规定”一个合格的开源合规项目必须存在哪些环节”，适用于所有行业、所有规模的组织。

如果合规是某种语言的特性，这份标准就该按语言分章节。它没有。

再看承载它的技术格式。合规产出物需要一个机器可读的形态，业内叫 SBOM，主流是 SPDX 和 CycloneDX 两个格式。其中 SPDX 本身已经是 ISO 标准（ISO/IEC 5962），而它的设计前提就是跨生态：SPDX 为每个许可证分配唯一标识符，今天 npm、cargo、go mod、maven 的 license 元字段都在原生使用这套标识符——所有语言生态，共用同一套合规词汇表。

还有一个更硬的例子，硬到不太好反驳。

Linux 内核。

2017 年底，Thomas Gleixner 给内核提交了一组补丁，加入了内核许可证标注规则文档。他给的理由是：

Due to formatting, typos etc. these “boilerplates” are hard to validate for tools which are used in the context of license compliance.

（由于格式、拼写错误等等，这些”样板文字”在合规场景的工具里很难被校验。）

结论是：内核要求所有源文件都必须在文件头带上精确的 SPDX 许可标识符。不是”建议”，是 requires。

然后最有意思的地方来了。这份文档逐一规定了 SPDX 标识符在不同文件类型里该怎么写：C 源文件用 //，C 头文件用 /* */，汇编用 /* */，脚本用 #，rst 文档用 ..，设备树用 //。

看懂这里面的东西了吗？

合规这个需求，高居所有语言之上——它从法律义务推导出来，跟用什么写无关。但落到实现层，它又必须钻进每一种载体里去，为每一种注释语法留出一个位置。

这不是”某种语言里没有合规”。这是”所有语言都得为合规腾出一个位置“。

5. 你们不是第一个想从零开始的人

这才是最讽刺的地方。

“每个语言团队各自理解一遍、各自实现一遍”——这个冲动不是我们独有的。它是行业级的顽疾，而且已经被标准文献点了名。

OpenChain 在讲自己为什么存在时，把供应链上的问题描述得非常直白：在一条供应链上，每个参与方都不得不为开源合规重建一套几乎完全相同的流程（each participant must recreate essentially identical processes for open source compliance），这一条被直接列为”供应链中重复的合规努力”（Duplicated Compliance Efforts in Supply Chains）。

一个国际标准之所以被造出来，就是为了终结”每家从零造一遍”这件事。

所以当我说”你们这边也需要做”的时候，我其实是在复述一件被 ISO 认证体系写了六年的常识。而对方的反应是——我们这里面没有这些东西。

换个角度算笔账，这个反射的代价才看得清。假设 JS 和 Go 两侧真的各自开工、各自琢磨一套：

  • 三套口径。 Java 侧一套判据，JS 侧一套，Go 侧再一套。最后手上不会有”公司级合规结论”，只有三份互不通约的地方性文件。
  • 一个乘法。 整体能力是各侧能力的乘积而非平均——某一侧归零，整体归零。这个模型我写过（自上而下的效能革命：打碎大锅饭的“质量乘法”与硬约束）。
  • 一个假象。 最坏的情况不是某一侧做不出来，是某一侧什么都不做，但不出声——而报告上”整体合规”四个字照样印得出来。

同一堵墙，我在把 P1 测试门禁推广到多语言团队时已经撞过一次（驯服巨婴：以“P1测试下压”与“复发红黑榜”终结顽固团队的推诿戏码）：Java 试点跑通之后，异构世界的第一反应从来不是”怎么对齐”，而是”我们这里不一样”。

6. 反过来推：从需求侧提问

写到这里，回到真正的落点——那句话是我在这一周里总结出来的：

遇到问题先从最基本的常识出发，来反推合理性，可能性。

我想把它操作化。”反推”其实就是把第 3 节那三个宾语，在开口之前就问完：

  1. 谁要这个东西？ —— 客户、审计方、法务。
  2. 他拿它干什么？ —— 举证。出了事要能拿出来辩护。
  3. 这个诉求会因为实现语言改变吗？ —— 不会。客户不关心你用什么写。
  4. 那么答案呢？ —— 它必然与语言无关；而既然与语言无关、又存在了几十年，业内必然已经沉淀出标准和现成工具。

四句话问完，”我们这里要不要做”这个问题就消失了。因为它从来就不是一个可以按语言回答的问题。

请注意这四句的顺序。它是从”谁要”开始的，不是从”我会什么”开始的。

这个顺序，就是需求侧思维和实现侧思维的分界线：

  • 实现侧思维的第一个问题是”我有什么“。 答案是我会的语言、我熟的框架。视野的边界，就是答案的边界。
  • 需求侧思维的第一个问题是”谁要什么“。 答案在组织外部，在客户那里、在法律那里。它不会因为你的工具箱改一个字。

而”我们这里面没有”这句话，只可能从实现侧的起点出发。

后记

最后说一件不太舒服的事。

“先有需求，才有软件”这次没能提前起作用，不是因为它不够对——恰恰因为它太对了、太老了、太熟了。

熟到它变成了一句”废话”。熟到我们默认所有人早就内化了它，不需要再被讲一遍。

可这次是需要讲的。而且首先不是讲给别人——是讲给我自己。因为我也花了两轮解释，才想起那张本该在开口之前就亮出来的牌。

还有一处分寸我得记下。

把结论直接亮出来、不给对方”我们做不了”的发言机会——这个做法这次确实有效，我不否认。但”有效“和”对“是两回事。它是把对方从参与者降级成了执行者。在一个信任已经缺失的组织里，这是必要之恶；但必要之恶仍然是恶，它不能变成默认姿势。

真正该被记住的，也许不是”以后直接给结论”。

而是：我们之间缺的从来不是一个结论，是一个判据。

有了判据，”我们里面没有”这句话，在说出口之前就会自己散掉——因为它找不到宾语。

最后留一句给下一个现场的自己：

老话不是没用，是它需要你恰好站在那个能被它击中的位置上。

Brooks 在 1986 年写下的那句话，在 2026 年的一间会议室里才生效。中间隔了四十年，和四种语言。

而那句话说的是——“同一个概念结构，在很多不同的表示之下，是同一个东西“。

它一直在那儿。

封面解读

这张封面是一排容器，摆在冷灰蓝的哑光平面上。它不是叙事，是一张对照表——四个壳，一个芯。

四个材质各异的容器 = 四套技术栈。 左边是棱角分明的金属盒，接着是通透的玻璃筒，然后是规整的陶瓷六棱柱，最右是一块表面粗粝的石头。四种材质、四种轮廓、四种触感，互不相像。这是”表示”的差异：同样是写代码，Java、Go、JavaScript、C++ 各有各的形制与手感，谁看谁都不像。

每一个容器内部，悬着同一颗暖色光球 = 那个不随壳改变的东西。 大小一样，形状一样，亮度一样。这就是 Brooks 那句话的形状：同一个概念结构，在很多不同的表示之下，是同一个东西。壳可以完全不同，芯是同一颗。

光是”从里面透出来”的，不是被外部照亮的。 这一点值得单独说。四个容器没有任何外部光源直射内部——金属盒的内壁是自己亮着的，玻璃筒里的球是自己发光的，连那块最不透光的石头，也有一道光从方形窗口里渗出来。需求不是被人从上头压进去的，它本来就在里面；你能换掉的是外壳，换不掉的是那团光。

冷灰蓝的环境 = 制度与理性。 合规、标准、审计，都是冷的东西；画面给它一个冷静的、哑光的、近乎仪器的底子。暖光只在容器内部出现，是整幅画里唯一的热源。冷的场景加上唯一的热，正是这篇文章的处境：在一个由标准和法务定义的世界里，唯一不变的那个东西，反而是最不显眼的那颗芯。

四个容器彼此隔离，没有连接。 它们并排，等距，谁都不挨着谁，中间还留着阴影隔断。这就是”我们这里面没有这些东西”的物理形态——四个工位，四套口径，四个自以为独立的宇宙。它们各自都亮着，但没有一束光横向穿过。

视角略微俯视、向右延伸。 画面不居高临下，也不平铺直叙，而是像站在台边侧身看过去——陈述的姿态，不是训导的姿态。

一句话总结：壳有四种，芯只有一颗；冷场景里唯一的热源，恰恰是那个大家都看不见、却谁都必须有的东西。

原始素材和基础语料（人工）

公司战略转向出海，因此需要做产品级 OSS License 合规分析——这在过往完全不在考虑范围内。领导要求 1-2 周内出东西。制品包解压后接近 4G，多年迭代，跨越 Vue / C++ / Go / Java 四个语言体系。

我先把 Java 侧做完，然后推着 JS、Go 侧去做。它们第一反应就是”我们这个里面没有这些东西”。在来来回回解释中，我总结出一句话：先有这个需求，然后才有这个软件；别搞反了。

这句也不是我原创，过往我在不同的书籍和专栏、文章里都看到过类似观点，这是我在这个正确的场合被迫想起来了。

归结到当前场景下，开源合规检查不是某种语言的特性。你要是说设计模式在 java 里用的多，其它语言内置这个我认，开源合规这踏马哪种语言不需要，这和语言没关系。视野居然只是局限在自己所接触到的那么点点地方，只要没接触过的就是没有。

遇到问题先从最基本的常识出发，来反推合理性，可能性。

这也提醒我，以后和它们沟通，直接拿出以上结论开始，别让他们自己发表意见，他们的第一反应肯定是这个做不了，得从零开始自己弄。这已经是过往多次的教训了。

续补记录（成文过程中新增或改写的观点，供事后回溯）：

1、前言背景（出海动因、4G 制品包、四个语言体系、一到两周窗口、Java 侧先行跑通、”推广”而非”推给”、推广前已与 AI 过完技术栈与基本流程）为成文时按用户补充说明写定，初版草稿此前言过于突兀。

2、第 1 节整节为新增：Brooks《No Silver Bullet》(1986/1987) 的 essence / accidents 二分，以及”同一个概念结构，在很多不同的表示之下，是同一个东西”这句，为成文时引入。它把原始素材中”这句不是我原创”的自认，反转成了全文的论据支点。

3、”把技术名词从句子里抠掉”这一动作，以及”设计模式抠掉语言就塌、合规抠掉语言还成立”的对比延伸，为成文时归纳。原始素材中只有”这和语言没关系”的断言，没有可执行的判据。

4、第 3 节”缺宾语”的三重补法（没有需求 / 没有工具 / 没有做过）为成文时新增；其中”没有工具”一节所附 go-licenses、license-checker、SPDX SBOM Generator 三处证据，来自成文时的资料核查，不来自原始素材。

5、第 4 节 ISO/IEC 5230、SPDX（ISO/IEC 5962）、以及 Linux 内核 2017 年 license-rules 补丁三组证据，为成文时新增。内核”逐一规定 SPDX 标识符在 C / 汇编 / 脚本 / rst / 设备树中的注释写法”这一细节，是全文最硬的一条反证。

6、第 5 节 OpenChain “Duplicated Compliance Efforts in Supply Chains” 的引述，以及”三套口径 / 一个乘法 / 一个假象”的代价推演，为成文时新增。

7、第 6 节”四问”（谁要 / 拿它干什么 / 会因语言改变吗 / 那答案呢）与”需求侧思维 vs 实现侧思维”的分界，为成文时新增。原始素材中只有”从最基本的常识出发，反推合理性、可能性”这一动作式表述。

8、后记”必要之恶”一段（把结论亮出来确实有效，但有效不等于对，它把对方从参与者降级成了执行者）为成文时新增，与原始素材”直接拿出以上结论，别让他们自己发表意见”存在张力，保留以自省。

9、封面：四个材质各异的容器 + 内部同一颗暖光内核 + 冷灰蓝平面 的视觉隐喻为成文时新设计。正文配图 6 张于 2026-09-18 生成，手绘笔记风格（暖奶油纸 / 黑线 / 玫红），图上标注仅用英文。第 1 张重出两次（初版自行多添了第三个词 SHADOWS）；第 5 张重出两次（初版标注 “4 x FROM SCRATCH” 被裁切截断，终版去掉全部文字）。
