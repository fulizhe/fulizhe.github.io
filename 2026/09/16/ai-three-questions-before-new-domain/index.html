新领域动手前，先问三句话

2026-09-16T15:20:00.000Z2026-09-19T09:35:29.291ZChina

前言

公司战略转向出海，于是第一次要做产品级的开源许可合规分析。这件事在过往完全不在考虑范围内。领导给的窗口是一到两周。

我选了最快的那条路：直接让大模型去扫最终交付的制品包。

包解开接近 4G，多年迭代，横跨四个语言体系。这件事我走了一周半。

我要写的不是”我不该用 AI”。我要写的是：那一周半里我一直在做的事情，我管它叫”验证”——但那套验证从头到尾只证明了一件事：我很勤奋。

而我从这一周半里带走的教训，不是一句感慨。

它是一张表，全文只有三行。我把它放在下一节，因为它是这篇文章的总纲，也是我写给下一个自己的指令。

1. 我从这件事里带走的，是一张三行的检查表

我原本的落点是这样的：

开源许可检测对我确实是新领域，但对软件开发行业来说并不是，这个东西在业内至少几十年的历史。以后遇到类似的事情，有必要克制心理的”赶紧开始”的冲动，逼迫自己先和 AI 聊一聊，让它总结下当前业内最佳的方案，挑选并迭代属于自己的。而不是上手就干，这是毛头小子的行为。

方向对，但它不可执行。

因为它把一个判据换成了一个动作——“先跟 AI 聊一聊“这个动作，要求你先知道该聊什么。你都不知道该往哪儿问，聊什么？而且它还把决策外包给了另一个随机源（后来我确实去聊了，那一轮不到五分钟，方向就对了；但那不是方法的功劳，是运气的形状）。

可执行的替代不是动作，是判据。动手之前，先问三句：

1. 这个领域存在多少年了？

2. 市场上有没有人把它做成了可购买的工具？

3. 有没有标准格式或公开数据集，允许第三方复核你的结果？

这三句的顺序不是随便排的。每一句都在拦一类错误：

第几句 问的其实是 答”是”意味着 我当时的状态
第一句 时间 有人踩过坑，坑已经沉淀成共识和工具 几十年历史——我完全不知道
第二句 市场 你面对的不是研究问题，是采购问题 BlackDuck、ScanCode、FOSSology 一抓一把——我完全不知道
第三句 可复核性 你的产出物能被第三方验证，也能被第三方证伪 SPDX 与 CycloneDX 就摆在那儿——我完全不知道

三个”我完全不知道”，恰好就是这张表存在的理由。

因为判据最要紧的性质，是它不要求你先具备领域知识。我在完全无知的状态下也能问出这三句；而且只要诚实地问，我必然会被导向第二句和第三句里的那些东西。反过来说——这三句之所以成立，正是因为我问的时候什么都答不上来。 我答不上来，不是判据失效的条件，是它生效的条件。

而”聊一聊”要求你先知道该聊什么。这一条差别，就是可执行与不可执行之间的距离。

三条全中的领域，”自研大模型扫描”根本没资格进入选项池。

下面七节，是我怎么一步步把自己走丢的。每一节都能被这三句里的一句拦住——我会在走到那一步的时候把话说明。

2. 我给自己造了一个”越验证越放心”的漏斗

我不是不知道模型会偷懒。这一点我在另一篇里写过（偷懒守恒定律：AI 是放大器，不是许愿机）：AI 是放大器，不是许愿机。所以我给它加了一层：贝叶斯验证漏斗——扫一遍不放心，就再扫一遍；两遍都命中，才提升置信度。

每一轮它都会还我一段非常专业的自然语言：这个文件里有 GPL，那个目录判定为 MIT，这个二进制包来源可疑。术语准确，格式整齐，语气笃定。

问题在于：我根本无法辨别真伪。 我只能一次次点击接受。

一周半之后我承认，我已经被架在那里了。而”已经投入一周半”这句话，悄悄从成本变成了继续走下去的理由。Barry Staw 在 1976 年给这个东西起过名字：承诺升级。赌桌上不肯走的人，都是这么留下来的。

但这一段里真正值得记下来的，是我搞错了焦虑的坐标。

我当时最焦虑的事情是”我无法辨别真伪”。这句话的主语是我自己，宾语是我的心理舒适度。而真正的风险完全在别处——开源许可合规的产出物，是要被第三方挑战的。 客户尽调、投资方审计、上游厂商追责，到那一天，我的证据链是什么？”我用大模型扫了 4G 制品包”？

命中了哪条规则、规则从哪来、误报率几何、漏报怎么兜底、如何复现——一条都答不上来。

你的隐忧是”我自己信不过这份报告”，真正的风险是”这份报告在合规意义上不可辩护”。

前者靠安慰，后者只能换方法。

而让我走到这一步的原因，用第 1 节的第三句话就能照出来：我之所以”无法辨别真伪“，是因为我的产出物没有任何第三方可以复核的形态。我缺的不是信心，是证据形态。

3. 伪重复：我一直在同一个偏差源上采样

贝叶斯更新有一个前提：观测之间条件独立。

我那一轮一轮的”再扫一遍”满足这个前提吗？不满足。同一个模型、同一套权重、同一批训练偏见、同一个 prompt 骨架、同一种偷懒方式。

所以那些看起来在收敛的置信度，收敛到的不是真相：

在同一个偏差源上采样一万次，后验不会收敛到真值，只会收敛到那个偏差的放大版。

生态学里管这叫 伪重复（pseudoreplication）。Hurlbert 在 1984 年的 Ecological Monographs 上专门写过这件事（原文），他的定义是：用推断统计去检验处理效应，而重复样本之间并不统计独立。他的说法很形象——拿一百棵同根生的苗当一百个独立样本，统计效率等于一。

那篇文章里还顺手统计了 176 篇实验研究：27% 存在伪重复；而在真正用了推断统计的研究里，这个比例是 **48%**。

所以我不该管那套东西叫验证。

它叫”对同一个偏见的重复确认“。

回到第 1 节第三句——要”允许第三方复核“，前提就是观测之间条件独立。两个互相不独立的观测，第三个人拿什么去复现它们的关系？我当时答不上第三问，正是因为我的东西根本没法被复核。

4. 我换了模型，但我没换方法

我也不是完全没想到这一层。我想到了同源错误，所以我的方案是：两个 agent，一个负责查，另一个用不同的模型做审查。

我换的是模型，不是方法。

Kim 等人在 ICML 2025 的 Correlated Errors in Large Language Models 里评估了 350 多个模型（论文），结论是我最不想看到的那种：

  • 在两个模型同时出错的情况下，它们在约 60% 的样本里给出的是同一个错误答案。而在 HELM 榜单上，如果纯粹随机地选错，这个数字应该只有 1/3。
  • 更刺眼的是趋势：模型越强、越准，错误相关性越高——跨厂商、跨基础架构同样成立。规模不制造多样性，规模制造同质化。
  • 他们做回归还发现：共享厂商、共享基础架构、相近参数规模，能解释模型错误一致性 34% 到 62% 的变异。也就是说，厂商换了、架构换了，但底下那批语料和那套对齐方式没换。

你以为你请了两个判官，实际上是一个判官的两次回声。

5. 难度是问题的属性，不是实现者的属性

有人会说：那就再换，三个、五个、十个模型。

Knight 和 Leveson 在 1986 年的 IEEE Transactions on Software Engineering 上做过一个更狠的实验（原文）。他们要检验的是”N 版本编程”的立论前提——互相独立开发出来的程序，会互相独立地出错。实验设计很干净：两所大学、27 个真正独立的实现、同一份规格、一百万次测试。互相不认识的人，不共享代码，不共享工具链。

结论是：假设被否决。 每个版本单独看都极其可靠，但同时失败的次数显著高于预期。

原因一句话：

难度是问题的属性，不是实现者的属性。

连互不相识的人都会在同一个难处上一起摔跤，何况两个共享网络规模语料的模型？它们共失败的位置，正是这个问题最难的角落。

而交叉验证的全部信息量，只存在于它们分歧的那一小部分里——分歧的地方你已经知道要看了。

一致的地方，它什么都没证明。

交叉验证消的是随机误差，消不了系统性缺失。信息不在文件里，加一百个模型也变不出来。

第 1 节第一句问的是年代。一个存在了几十年的问题，它的难点早就被人写进论文里了——我却在用”再加一个模型”，把 1986 年那个已经被否决的假设重新发现了一遍。

6. 有些活本来就不该交给概率模型

再回到这件事本身：我到底在让模型干什么。

版本号、LICENSE 文件、文件头声明、包元数据——这些不是”判断”，是结构化事实提取，是查表。 用两个概率模型去对赌一个正则表达式就能给出的答案，是把确定性问题做成了概率问题。

而真正的分野在证据形态上：

做法 产出 性质
扫描工具命中 文件路径 + 行号 + 命中规则 + 规则来源 可举证
模型说”这里有个 GPL” 一段自然语言 意见

合规交付物只能收前者。

这件事我在别处也写过（性能调优的“猜谜”玄学：可观测性虚无下的乱拳与神棍）：没有可观测性托底，性能调优必然退化成猜谜和拜神。本质是一回事——无法举证的判断，无论出自人还是模型，都无法被复核，因此也无法被信任。 模型只是让这个过程变得更快、更自信、更贵而已。

第 1 节第二句问的是市场。市场上早就有人把这件事做成了可购买的工具——这本身就说明这件事的答案形态早已被固定下来：不是一段自然语言，是一条可举证的记录。

顺带说一句信息卫生。检索资料时，我翻到过一篇中文的扫描工具”测评”，声称”10 GB 代码库初始化扫描 2 秒””许可证识别准确率 7%”，还引了一份”Linux 基金会 2026 基准报告”和一个查不到的申请代码。数字自相矛盾，没有出处——SEO 软文。

做新领域选型，只认官方文档、官方 issue、和有 DOI 的论文。 而当时的我，恰好是那种最容易被这种数字骗到的人：我连这个领域有哪些标准都不知道，拿什么去质疑它？

7. 真正让我后背发凉的，是工具的默认行为

转折出现在一周半之后。我把背景整理了一遍发给 ChatGPT，它给出的第一版方案里有一条原则，我认为完全正确：

Unknown > False Negative——宁可报”无法确定”，也不能把”没发现许可声明”当成”没有许可”。

这条原则如果直接用开源扫描工具的默认配置去实现，会被工具从底部击穿。

ScanCode 官方文档对 --timeout 的定义（文档）：

Stop scanning a file if scanning takes longer than a timeout in seconds. Default: 120
If some file scan exceeds the specified timeout, that file isn’t scanned anymore and the next file scanning starts.

超时的文件被静默跳过，在输出里表现为”没有许可命中”。而整条流水线无法区分”扫了、没有”和”没扫完”。

我精心设计的反漏检原则，被工具的默认行为静默废掉，不留任何标记，也不报任何错。

这不是理论担忧，因为慢是常态。ScanCode 官方自己的 Runtime Performance Reports 里记录过一次真实扫描（记录）：195,676 个文件，16.7 小时，约 3.25 文件/秒——那还是单线程的老版本。Antelmi 等人在《Journal of Supercomputing》2024 年那篇里测到的是平均 6 秒/文件，平均文件才 26.6 KB（论文）。

按方案里估的规模算——一万两千多个文件——大约 21 小时。这还只是扫描一项，不算二进制分析、规则引擎、报告生成。

内存也不客气。官方 issue 里有人记录过（issue #3711）：一个 1.3 MB 的 JSON 文件扫了 6 分 27 秒、吃掉 6 GB 内存；一个 XML 文件扫了 7 分 17 秒、吃掉 11.8 GB，报告者不得不把超时从默认的 120 秒提到 600 秒。更麻烦的是扫完之后内存不回收，后面的文件继续在高水位上跑。

慢只是延期；静默漏检是出具一份看起来完整、实际有洞的报告。

而这个模式，和我最开始那个隐忧，是同一个东西的两张脸：

任何自动化环节的默认失败模式，都会伪装成成功。

模型偷懒是一种，工具超时是一种，CI 里的 UNKNOWN 不阻塞也是一样——一份 CI 是绿的、发布照走、报告里躺着二十几个”无法确定”的合规报告，三次之后就不会有人打开它了。

那才是”模型不可靠”这句话的一般化形式。我真正担心的不是它不靠谱，而是它不靠谱的时候不会举手。

这是我第一次认真去读那个工具的官方文档。读完之后我才发现：第 1 节那三句里，第二句本来会把我直接送到这些文档面前。 雷不是没被记录，是我没去找记录。

8. 我不是想不到，是想到了不作为

写到这里，得说清一件事，否则这篇文章会冤枉我，也会冤枉很多读它的人。

我不是“只知道交一份报告、没有长期视角”的那种人。恰恰相反——在动手之前一周半，我就已经提出过：这件事要交长期能力，不能交一次性报告。我跟技术总监提过了。

我也不是不知道模型不可靠。这一点我一开始就写下了，”我无法辨别真伪”是我一路都在说的话。

两个我都想到了，我还是走了那条路。

所以问题从来不是”想不到”。我的毛病得单独拆出来看：

  • 毛头小子的病：无知无畏——不知道有风险，所以冲了。药是摄入知识。
  • 我的病：有知而不敢停。药是”一张自我签发、允许自己停下来的许可“。

两种病的药完全不同。我读了二十年书，摄入从来不是我的短板；我缺的是那张许可。

证据就在手边：一周半之后我才把背景发给 ChatGPT，它给出的第一版方案，一轮对话、不到五分钟，方向就对了。 而我预想中”半途停下来去研究最佳实践”的成本，是凭空假设出来的——我不是停不起，是默认自己停不起。这个默认从未被验证过，就被我当成约束条件接受了。

（这里有一处得自曝。那次对话里，对方也犯过一次同类错误：它根据我提到的时间词，推断”交能力不交报告”这个想法也是前一晚才产生的，被我当场纠正。它是在用推断替代证据——而整篇文章的主题恰好就是证据与意见的分野。审阅者会犯被审对象的病，这件事我记住了。）

而这恰好把第 1 节那张表最要紧的地方逼出来了：”跟 AI 聊一聊“这个动作我最后确实做了，而且五分钟就拿到了正确方向——但这只说明它这次起作用靠的是运气，不是结构。我这次运气好，碰上了一版能用的骨架；下一次换个领域、换个提问姿势，同样的动作照样能把我带进另一条一周半。

判据不一样。它不依赖我碰上谁，只依赖我肯不肯诚实回答那三句。

顺带补一句诊断。我在另一篇里给”不作为”分过诊（不作为的三种病因：不为、不能与不知）：不为、不能、不知。这次这一格三种都不沾——我不是不想做，不是不能做，也不是不知道。

我是知道了，但”停下来”这件事，我没有取得自己的许可。

后记

那张表我不复述了，它就在第 1 节。我只在后面补三条纪律，写给下一个要踩进新领域的我：

  1. 答不出第二句，不许开工。 如果我说不出”这个领域有哪些成熟的、可以买或者可以直接用的工具”，那我就还没有资格动手——因为这说明我连问题长什么样都还不知道。
  2. 三句话写在开工之前，不是停下来的时候。 它们唯一有效的时刻，是在我还没投入任何沉没成本之前。等走了一周半再问，我已经不是在做判断，是在给自己找台阶。
  3. 先测一次”停下来”的成本，再采信它。 我以为中途研究最佳实践要花一周半，实际是五分钟。我从来没有验证过这个成本，就把它当成了约束条件。

至于那份 AI 方案的骨架，我逐条审了一遍，标出 12 处问题，4 条 P0（附在补充里）。我不打算把这篇写成”AI 救了我”。真实的张力在别处：AI 能在五分钟里给你一个正确的骨架，但骨架里的地雷，要你自己带眼睛去挖。 反过来也一样——我在另一篇里说过（AI只是枪，不是免死金牌），AI 只是枪，不是免死金牌。今天再补一句：它也不是替罪羊。那一周半是我自己走完的。

一周半里我唯一做对的事，是最后终于承认自己该停。

这个承认花了七天半。而它本来可以在第一天的十分钟内完成。

最后留一句给我自己：

反思真正落地的标志，不是你今天想明白了，是下次那三句话，在打开聊天框之前就已经问完了。

补充 - 那份方案里的四颗雷

我把那份 AI 方案逐条审了一遍，标出 12 处问题，其中 4 条是会让整个交付直接失败的。它们很能说明”骨架对”和”能跑”之间的距离。

# 问题 为什么是致命的
1 吞吐与内存预算完全没算 方案排的 Day 1 要在一天内跑完扫描全流程。按官方实测吞吐（6 秒/文件），单扫描一项就要 21 小时以上；加上官方 issue 里记录的 11.8 GB 峰值内存，很可能被 OOM 打死。排期从第一步就是超预算的
2 --timeout 静默跳过文件 方案自己定了”Unknown > False Negative”，实现时用默认配置，这条原则就被工具从底部击穿（见第 7 节）
3 三路检测器只落地了两路 架构图画了三个并列的检测器，实际只讲清两个。而对纯 C/C++ 静态编译产物，另一个的能力接近于零——静态编译后 buildinfo、MANIFEST、dist-info 这类嵌入式元数据全都不存在，没有东西可提取。这块覆盖度在矩阵里是空格的，就不该叫”合规分析能力”
4 UNKNOWN 不阻塞，组织行为上等于 PASS 方案里 UNKNOWN 和 REVIEW 都只是”出一份报告”、不影响流水线。”不知道”因此变成了一个不需要有人负责的空白。正确做法是反过来：宁可让客户看到”我们无法确认 X”，也不要让客户以为”我们确认了 X 没问题”。 前者是能力边界，后者是虚假陈述

骨架是对的，四条补上就能真的交付。但骨架是 AI 的，这四条是我自己挖出来的——这就是第 1 节那第三句话的具体形状：确定性问题不能交给概率模型，而概率模型给出的方案，也必须由人来判定它是否成立。

封面解读

这张封面是一个岔路口，画在一块冷灰蓝的哑光金属平面上，像蚀刻进去的线路图。它把全文压缩成了一次二选一——而这一次二选一，发生在我动手的第一天。

三根等高的空白立桩 = 那三句话。 它们立在左岔的路口，等距排列，桩身光洁、没有刻任何字。这个”空白”是刻意的：判据不需要内容，它只需要位置。三句话之所以有用，恰恰因为它们是空的——你不需要先懂这个领域，就能把它们问出来。

左岔：又短、又直、又干净 = 判据导向的那条路。 它从岔口直直通向画面远处的冷白光口，路面没有任何车辙。这是文章第 1 节那张表的样子：三句问完，你被直接领到现成的工具和标准面前，全程不需要你自己发明任何东西。

右岔：绕成巨大螺旋、车辙密布 = 我走掉的那一周半。 这是画面里面积最大的一块，也是唯一被反复碾压、磨到发白的地方。它看起来最努力——所有的磨损痕迹都在这里。但螺旋最终是闭合的：它转了很多圈，回到原点，一毫米也没有前进。这正是第 2 节的贝叶斯漏斗与第 3 节的伪重复：痕迹最多的地方，恰恰是没有位移的地方。

两条路共享同一个岔口。 起点相同，投入相同，甚至连”想不想做好”都相同。唯一的分野，是路口有没有立着那三根桩。所以这张图里的差异不是勤奋程度的差异，也不是智力差异——它是”有没有判据”的差异。

唯一的冷白光在左岔尽头。 画面里所有光源都来自那一侧；螺旋那一侧没有光，只有磨损。光不是奖赏，是可见性：有判据的那条路，结果是看得见的；没有判据的那条路，剩下的只有自己以为的勤奋。

用冷色而不是暖色，和这幅画的立场有关：这不是一份控诉，是一张分诊表。画面里没有第三个人，没有指责的对象——两条路都是我走的。

一句话总结：同一个岔口，唯一的分野是路口有没有立着那三根桩——判据的有无，决定了两条同样努力的路，一条通向答案，一条通回原点。

原始素材和基础语料（人工）

公司战略转向出海，因此需要做产品级 OSS License 合规分析——这在过往完全不在考虑范围内。领导要求 1-2 周内出东西。和技术总监初步沟通后，选择的方法是：直接让 LLM 扫描最终软件制品包。制品包解压后接近 4G，多年迭代，跨越 Vue / C++ / Go / Java 四个语言体系。历史遗留：过去完全没有考虑过这方面，相关人员没有意识，引入依赖完全靠当时的心情，也不会从正规网站获取。

用”LLM 全目录扫描”的方式走了约一周半。期间一直有隐忧：LLM 已被证明是能办事的，但偷懒是常态；而 OSS 检测本身对我、对公司都是处女地，都是头一次接触。即便有 harness agent，对每次扫描给出的答案我根本无法辨别真伪，只能一次次点击接受。我接受了”贝叶斯验证漏斗”的思路，但承认那是基于本能做出来的决策，每次执行心理压力都重一分。处境：已被架在那里，不好半途去研究最佳实践，于是一路走到现在。

昨晚”不详的预感达到顶峰”，我把背景知识发给了 ChatGPT，结果它给出的第一版方案就深得我心：在满足快速 MVP 的前提下，基于现有状态，借助开源工具快速检索，以及用 Python 编码扫描制品包内容，进行彼此交叉验证，来实现要求时间内最大可信度的交付。

oss 检测对于我自己确实是一个新领域，但对于软件开发行业来说可并不是，这个东西在业内至少几十年的历史。以后遇到类似的事情，有必要克制心理的赶紧开始的冲动，逼迫自己先和 AI 聊一聊，让它总结下当前业内最佳的方案，挑选并迭代属于自己的。而不是上手就干，这是毛头小子的行为。

（后续更正）”ChatGPT 那一版方案，前后不到五分钟”——不是一晚上，就是一轮对话的功夫。确实是我自己的问题。

（后续更正）SPDX 与 CycloneDX 这些标准我都不知道，SBOM 还是从 Java maven plugin 插件学习时偶尔知道的。

（后续更正）”交能力不交报告”这个想法，我一周半前就已经形成，并且和总监提过了。

（后续更正）我确实想到了”同源错误”问题，所以采取的方案是：两个 agent，一个查，另一个用不同模型审查。

续补记录（成文过程中新增或改写的观点，供事后回溯）：

1、”判据优于动作”这一命题、以及「领域存在多少年 / 有没有可购买的工具 / 有没有允许第三方复核的标准格式」这三问，为成文时归纳。原始素材中只有动作式的落点（”先跟 AI 聊一聊”），三问是在讨论中被逼出来的替代方案。第 1 节整节为新增，并把它提到题眼位置。

2、”焦虑坐标错位”（隐忧是”我自己信不过这份报告”，真正的风险是”这份报告在合规意义上不可辩护”）为成文时新增的表述，依据是原始素材中”我根本无法辨别真伪”与”出海产品要对客户尽调”两条的并置。

3、”失败不会举手”作为本文对”模型不可靠”的一般化形式，以及”任何自动化环节的默认失败模式都会伪装成成功”这一总结，为成文时新增。

4、第 7 节的 --timeout 静默跳过、官方性能报告、官方 issue #3711 三组数据，来自对方案的逐条评审过程（那份评审同时产出了补充里的四条 P0），不来自原始素材。

5、第 8 节”两种病，两味药”（毛头小子的病是无知无畏，药是摄入知识；我的病是有知而不敢停，药是一张自我签发的许可）为成文时新增的分型，是原文”这是毛头小子的行为”这句自我定性的反证。

6、第 8 节末尾”AI 也犯过一次同类错误（用推断替代证据）”一段为依据实际对话如实补入。

7、后记三条纪律为成文时新增，用来把题眼从”想明白”变成”可执行”。原后记为感慨式收尾。

8、封面：岔路口 + 三根空白立桩 + 螺旋车辙的视觉隐喻为成文时新设计。第一次出图立桩只数出两根，与”三句话”不符，已重出（v2）。
