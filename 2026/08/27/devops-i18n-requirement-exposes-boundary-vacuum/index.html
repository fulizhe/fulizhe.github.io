一个国际化需求照出的"边界真空"：谁来对端到端结果负责？

2026-08-27T13:00:00.000Z2026-09-05T02:48:25.038ZChina

前言

今天有两件事，连在同一个需求上，我觉得该一起记下来。

第一件：测试主管第一次明确地、有意识地顶了回去——“这是你们研发内部的事”，不肯再替研发去手工替换文件。

第二件：顶回去之后，这需求滚到了我这儿。我是那个 Jenkins 的。我也是被卷进来，才第一次知道：这件事跑了一年多，第一步居然是”手工传递“——研发改完，不发仓库触发流程，而是把文件丢给测试去替换。

一年多的荒诞，被这两下同时照亮。我不想只写”测试勇敢”，也不想只写”我搞定”——它们是一块标本的两面。

1. 标本：一个没进禅道的紧急需求

先摆标本。帮助文档国际化，名义上三个”负责人”：语言切换没实现，归 XXXX；文档中英混杂，归 apifox 维护人员；jenkins 流程失败，归 YYYY。

三个人，三块活，过去一年多零沟通。最荒诞的是第一步——XXXX 改完，不是提交仓库触发流程，而是发给我方测试，让测试去手工替换。

这叫”人肉API“：jenkins 链路明明在，真正流转价值的却是一个人在聊天框里把文件丢给另一个人。pipeline 在，人肉也在，这种”伪自动化“比没有自动化更隐蔽，它用”已经自动化了“的幻觉，恰好盖住责任分散。

但这里有个关键细节，我一开始也没想透：国际化这种，根本不在禅道的捕获范围里。 禅道只收”新需求“；像国际化这样早就自成一套流程的遗留项，测试和我都不好在那里面硬梳理轨迹、强迫改变。它活在聊天记录和某人的习惯里，既绕过了”追踪基石“，也不在任何卡口兜底范围内。

所以这不是”紧急 bypass”那么简单，而是一个已知的边界：两年地基扎实，但只铺到了”新需求”这一格；遗留的、已成型的流程，是另一片还没铺、也不该硬铺的地。

技术上它本可一次性根治：XXXX 提交 git，jenkins 触发，吐出更新版本；apifox 有更新，jenkins 照样拉取。整条链路本该自洽、自动、无人肉参与。可现实是每个人只扫自己门前雪，链路断成几截。

没人把这串环节当成”一个完整的问题“去 owner。系统的质量是乘法的——只要有一个环节人肉、断裂、无人认领，整条链路就是零。拖了一年多，不是因为难，是因为”对端到端结果负责的那一个人“一直缺席。

再往下挖一层，问题不只是”链路断了”。这套流程的”验收标准“里从头到尾只有”一次性“——没有自动化、没有常态化、没有无人化的意识。每一步都在靠某个人的临场操作补位：研发手改、测试手替、jenkins 在后面空转。所谓”人工魔法“，就是把本该系统兜底的事，全压成了”特定的人在场才能转”。这也解释了它为何拖了一年多：每一次”解决”都是一次人工补丁，从没人设计过”让这件事不再需要人”。

2. 为什么是现在：两年地基，让一线敢划边界

测试主管那一下顶回去，不是今天突然有骨气。它是我们过去两年多埋下的三根管线的总闸，在这一刻合上。

第一根管，禅道建设——分两步走，步步朝着”把归属钉死“去。 先按人工线下流程改禅道、最大化适配，等习惯养成就逼全线上化，奠定”追踪基石“；再逐步收紧卡口：需求描述强制字数、格式，关掉易乱操作的按钮，新增”是否要测试“”是否需要更新文档“等字段，把边界焊进卡片。

第二根管，自动化加快循环周期——反而把手动压力推到临界点。 自动化让构建部署转更快，更多版本更高频砸到测试面前，压力不是小了是大了。恰恰是”被加速的周期逼到墙角“，逼出了边界意识——当手动承接根本承接不过来，”什么都替研发兜底“从道德选择变成物理不可能。压力，成了边界最好的老师。

第三根管，测试人员思维的灌输。 前两根是地基和外力，这一根是内功：测试的价值不在”替研发把活干完“，而在”对需求/BUG 本体给出独立的质量判断“。认知变肌肉记忆，那个”不”字才说得出、接得住。

测试主管顶回去的那一刻，是”禅道清晰度 × 自动化压力 × 思维内功“三重乘积的兑现。但同一个人，顶回的恰恰是”禅道边界之外掉出来的遗留流程“——这又反过来说明：地基铺到了新需求，可”已成型的旧流程“这一格，仍在边界外。

3. 我被卷进来，才知道第一步是手工传递

顶回去之后，这需求没处去，滚到了我这儿。我是那个 Jenkins 的。

我本来以为流程是通的。直到被卷进来，才第一次知道：居然第一步就是手工传递——XXXX 改完，不发仓库，直接丢给测试替换。所谓的 jenkins 流程，在第一步就断了，后面再自动也是空转。

所以我花了一小时，规定了这个流程：XXXX 提交 git → jenkins 触发 → 自动产出更新版本；apifox 有更新 → jenkins 照样拉取；测试不再手工替换，只盯结果。

这一小时值得记一笔，不是因为我多能耐，而是因为它照出一个事实：这事一年多人没解决，不是难，是”对端到端负责的那个人“一直缺席。 地基（追踪、卡口、自动化）都在，只是没人把这串环节当成”一个完整的问题“去 owner。我刚好是那个被卷进来、又有 Jenkins 视角的人，于是顺手把格子补上了。

4. 禅道边界法则，与地基的裂缝

顺着这事，我把那条规则落清楚，叫”禅道边界法则“。

测试只盯”禅道需求/BUG 本体“：这条需求或这个 BUG 本身是什么、该不该过。至于它”是谁导致的“，由研发内部一层层传导，测试最多提醒一句”时限要到了“，而不是被研发当皮球到处踢。

这条法则背后，是一个更根本的概念缺位：”问题负责人“。当前团队里，”负责人”是切片的——语言切换归 XXXX、文档归 apifox 维护人员、jenkins 归 YYYY，每人只对自己那一片负责。于是没人对”这件事到底算解决了没有”负责，自然也没人去推动它从 A 流到 B。

所以我推着测试这么干：测试只管禅道需求/BUG 本体，盯死它；其余的，让研发自己内部沟通。这不是偷懒，是借人性的力——哪怕出于本能，当事人在接到一张甩不掉的卡时，也会想办法把问题从自己手上弄出去。既然甩不回测试，那就只能往前推、往下落，直到有人把它修掉。恰恰是”甩锅本能”，成了推动事情发展的动力。 边界划清之后，不靠觉悟，靠结构把责任逼回它该在的地方。

这条法则能成立，前提是禅道把归属钉死。但本次标本也提醒我们：禅道只收”新需求“，像国际化这种已成型的遗留流程，本就不在它的覆盖里——测试和我也不好硬去梳理轨迹、强迫改变。

所以这一格的启示不是”赶紧把遗留流程也搬进禅道“，而是：在 ZenTao 的边界之外，用一条轻量的”交接流程“把日常的归属钉死——我那一小时定的，正是这个：不强迫改变既有轨迹，只规定”提交 git → jenkins 自动产出，测试不再手工替换“。而这次也是”借机“：借这个需求被顶回来的契机，把边界外那格顺手补上。至于”根治这条遗留链路“这种动作，它本身是一条新需求，本该正大光明立卡进禅道，那是下一节要推演的。

5. 推演：这三个人的分工，本来是凑得出来的

再往下想一层，我发现上面那句”边界外还没铺”说得还不够狠。

先看一个被所有人忽略的事实：这三块活——语言切换、文档去混杂、jenkins 链路——加起来本就是完整的端到端。不缺角色，不缺能力，不缺工时。XXXX 改得动代码，apifox 维护人员管得住文档源，YYYY 摸得到流水线。三个人的分工，是凑得出来的。

那到底缺什么？缺一张把三个人串在同一张卡上的需求单。

所以可以做个反事实推演：假如这件事当初立成一条禅道需求，会发生什么？

  • 需求描述强制字数与格式——那就必须一次把”三块活分别要交付什么”写清楚，写不清就提不进来。含混的一句”文档国际化有问题”根本过不了卡口。
  • “是否要测试”字段勾上——测试的介入点被钉死在”最终版本产出之后“，而不是”中间帮忙替换一下文件”。
  • “是否需要更新文档”字段勾上——文档归谁，在流转开始之前就已经标死，不会退化成”XXXX 改完丢给测试”。
  • 卡必须有 owner——哪怕下面挂三个子任务，父卡头上得挂一个人。这个人就是”对端到端结果负责的那一个“，不需要格外的觉悟，是字段逼出来的。
  • 卡不闭环就一直挂着——看板上那张迟迟不肯变绿的卡，本身就是时限压力。乘法模型不再靠谁的自觉去维护，而是被闭环规则强制执行。

结果是什么？测试想要的那个”一次性”，会被自动满足。 不是靠测试主管吵一架吵出来的，是禅道的流转规则天然给的：一次交付，一次验收，中间不当搬运工。

但要把话说全：立卡满足的是”一次性有人接、有人验”，这是地板，不是天花板。它没解决另一层——验收标准里有没有”常态化、自动化、无人化”的意识。如果团队只满足于”这次交付了、这次验过了”，下一次还是靠人临场补位，那流程底下垫的依旧是人工魔法。统筹能靠立卡长出来，但”让这件事不再需要人”的系统意识，是比立卡更靠后的下一步。

推演到这儿，我得修正前面那句话。禅道”没覆盖统筹场景“，其实是我的误判——遗留流程的日常轨迹不必硬搬进禅道，这仍然对；但”根治这条遗留流程“这个动作本身，是一条彻头彻尾的新需求，它完完全全在禅道的覆盖范围之内。

它一年多没进来，不是因为禅道不能，而是没有人把它当成”一件事”去立卡。所有人都把它当成日常杂活、当成一句抱怨、当成”我改一下你替换一下”的口头交接。在系统里没有卡，在组织里就没有 owner。

这也顺手回答了标题里那个问题——“谁来对端到端结果负责”。答案既不需要新设一个统筹岗，也不需要指望谁格外有觉悟：是那张卡的卡主。 统筹不是一个人的美德，是一张卡的属性。

6. 补充 - 关于”自动化反而加压”

很多人以为上自动化就是为了给测试减负，这是天真。自动化加快的是”循环周期“，不是”工作量“——周期越短，单位时间砸到测试面前的版本越多，手动承压反而上升。真正的红利不在”测得更少“，而在”逼出更清晰的边界“：当手动承接注定承接不完，团队才被迫去定义”什么必须自动化、什么必须研发自己扛“。所以别用”减负”去 KPI 自动化，要用”逼出边界与 owner“去衡量它。

后记

写到这里，我反倒踏实了。

组织的进步很少是某一下的顿悟。测试主管顶回去，是两年播种第一次抽穗；我被卷进来一小时定流程，是顺手补上一格裂缝。两件事同一天发生，说明地基开始流水了——只是还没流满每一格。

至于 XXXX、YYYY 们什么时候长出”对结果负责“的自觉，那是另一根还没铺完的管子。但至少，水，已经开始从这一格流向那一格了。

而这次最该留下的一句话其实是：再有人把这种事当口头交接递过来，第一反应不该是接，也不该只是顶回去——是先去立一张卡。卡立了，统筹自己就长出来了。

封面解读

封面那张图，画的是同一件事的三重缺失：左侧一个小球被箭头顶回边界线（测试把皮球顶回研发），中间链路里一个明显的空缺（jenkins 手工传递断链），右侧一格没铺满的网格（禅道地基有格未铺）。三处空洞拼在一起，就是标题里的「边界真空」。而破局的两下——测试顶回去、我一小时定流程——图里没有画成英雄，只是画成把手伸过去、把那几格补上的动作。水，开始从这一格流向那一格。
