先让问题存在

2026-10-21T13:10:00.000Z2026-10-31T12:37:03.301ZChina

前言

三天里发生了两件事。

周一，我给部门里另一位产品负责人讲了 单体应用的监控，只服务三件事 那一套东西。他手上的产品，公司里迭代了六七年，可观测性是零。今天下午，他已经开始往测试环境推 MVP 了。

而我这套东西，在另一个现场，用了四年。

同一套工具，同一个作者，两个时间尺度。差别当然不在方法——方法一个字都没改。差别在约束：他那边没有对手，我这边对手是稳态。

但这几天我真正想明白的，不是“环境不同、见效快慢不同”这种老生常谈。我想明白的是：我这四年干的，根本不是“解决问题”。

我在生产问题。

1. 一个六七年没人解决过的产品

先看这位同事的现场。

他的系统不是单体，也不是真微服务。按我之前写下的话说，这叫伪微服务（这个概念是我自己起的，见原文）：按微服务的方式设计和拆分，几十个服务，最后全部部署在同一台机器上。

这个结构有两个后果：

  • 内存打架：一台 16G 的机器塞几十个 JVM，谁多吃一口，别人就可能被 OOM Killer 干掉。而被砍的通常不是内存涨得最凶的那个，是这一轮刚好排在评分最前面的那个。
  • 启动顺序锁死：A 依赖 B，B 依赖 C，C 启动时要跑一段极慢的初始化。C 没起来，B 起不来；B 起不来，A 也起不来。一个慢，全链死。

于是在这套结构里，“事故”长成什么样？——你只看得见报错的那个人。

A 报连接超时，日志里全是 A 的异常栈。你去查 A，A 说我只是在调 B；你去看 B，B 说我在等 C；你去看 C，C 的日志干干净净——因为它只是“慢”，它没犯错。而 OOM Killer 那一刀，记在 dmesg 里，不在任何一本应用日志上。

在伪微服务里，报错的位置和故障的位置，几乎从来不在同一个服务上。

再叠一层：产品跑了六七年，从来没接过探针，没有指标，没有链路。出事了怎么办？

靠运气。

运气好，翻两页日志就翻到了那一行异常。运气不好——hang 住、变慢、接口偶发超时——那就是撞上硬岔子了。这时候的动作是：重启一下、参数调大一点、回滚个版本、再等等看。

有时候真就好了——因为你恰好重启了那个在 OOM 边缘的服务，腾出了几百兆；也可能因为重启的顺序恰好让 C 先起来了。但下一次同样的动作，可能就没用，而你不会知道为什么。

每一步都做，每一步都不知道为什么做。做好了松一口气，没做好再来一轮。

于是开始补日志。今天补一条，明天补一条，上下游一起跟着耗，耗到最后也未必能定论。

补日志不是排查。补日志是打手电。 而手电的悲哀在于：它只能照亮你已经想到的地方。你想错了方向，光就打错了地方——你甚至不知道自己打错了地方，因为黑屋子里没有别的东西可以对照。

六年多里，这些问题从来没有被“解决”过。但它们也从来没有被“放弃”过。它们悬在那儿，像一个说不清病史的老毛病，来了就熬，走了就忘。

悬着的东西不叫问题，叫命。

2. 血压计之前，世上没有高血压

我想先说一个医学史的事实。

在血压计被发明之前，世上没有“高血压”这个病。

有的只是头晕、耳鸣、眼花、中风。这些是症状，也是命数——老人头晕，那是上了年纪；中风倒了，那是运气不好。没有医生会告诉你“你的收缩压 165，属于二级高血压，需要长期服药”。因为没有任何一个数字可以支撑这句话。

血压计出现之后，事情变了。一个读数，让“头晕”从一种命运变成了一项指标；再往后，才有分级、有指南、有降压药、有一整套干预路径。

请注意这个顺序：

不是先有高血压，再发明血压计。是先有血压计，才有高血压。

这不是文字游戏。福柯在《临床医学的诞生》里讲的正是这件事：现代医学的转折点不是发现了新病种，而是换了一种“看”的方式——症状不再被当作疾病的表象，疾病本身成了可以被凝视、被定位、被切开的对象。

技术侧完全同构。

探针装上之前，“卡顿”是一个形容词。它只能出现在口头描述里：“最近有点慢”“高峰期有点顶不住”。形容词没法被排期，没法被验收，也没法被证伪——你只能说“我感觉好点了”。

探针装上之后，同一件事变成：P95 = 2.3s，集中在 order/query 端点，从 10:32 起，伴随 GC 次数上升三倍，同时段 DB 连接池打满。

它从一个形容词，变成了一个句子。 有主语（哪个端点）、有谓语（超时）、有状语（从几点起）、有宾语（哪个资源）。而只有句子，才能被讨论、被指派、被修掉。

所以这句话得说清楚：

测量不是在发现问题，测量是在发明问题。

这也是为什么他那套东西一上去，就能做到秒级定损。不是因为他的团队比我的团队勤快，是因为那边第一次有了可以指认的东西——问题点被第一时间看到，责任范围当场收窄，剩下的只是修。

3. 请神的人，手里没有神像

我在另一篇里写过这个画面（顺序比努力贵：四年复盘）：一群受过计算机科学训练的人，排查问题时跟请神一模一样。

当时我把根因归到“没有反馈”——请神之所以是请神，不是因为它迷信，是因为它没有可复现的因果，你无法判断这次灵验是因为你诚心，还是因为本来就不下雨了。

这个判断只对了一半。还有更前面的一层：

请神的人，手里连神像都没有。

重启一下，好了。你不知道是重启解决的，还是它本来就要好了。回滚个版本，好了。你不知道是版本的问题，还是恰好过了那个时间窗。你想“验证”一下，可你连要验证什么对象都说不出来——因为那个对象从来没有被定义过。

这不是方法选错了，是宾语缺失。

杜威在《逻辑：探究的理论》里把这件事讲得很干脆：探究的起点不是“一个现成的问题”，而是一个不确定的情境；问题是人从这个混沌的情境里制定出来的，不是从天上掉下来的。换句话说——

“问题”不是一个被发现的名词，是一个被制造的动词结果。

这在工程上一点都不玄。你觉得“系统慢”，那是情境。你把“慢”拆成“哪个接口、多慢、什么时候开始、跟什么同涨同落”，那才叫问题。而拆分这件事，靠的不是聪明，是有没有东西可以拿来拆。

可观测性提供的，就是那堆可以拿来拆的碎块。

没有它，你不是在解决问题，你是在一堆说不清的状况里，赌哪个动作能把状况按下去。按住了是运气，按不住是常态。这套东西能维持六七年，只能说明一件事：

这个产品的失败成本，六七年里从来没有被真正结算过。

4. 我在四年里干的另一件事：发身份证

现在回到我自己。

四年里我干了两条线。一条是技术侧的探针与观测台，另一条是组织侧的禅道二次开发。这两条线过去在我心里是两件事——一件对机器，一件对人。

这几天我才把它们合成一句话：

两条线干的是同一件事——给问题发身份证。

技术侧：让每一次异常都留下端点、耗时、时间戳、调用链。它回答“是哪一次”。

组织侧：让人、单、时、状态全部线上化，工时、流转、卡点、停留时长都能查。它回答“是谁那一段”。

过去，“这个需求拖了三个月”是一句抱怨。它可以说，可以辩，可以被“最近确实比较忙”挡回来。现在它是一条记录：哪天提的、在哪个环节停了多久、上一次状态变更是什么时候、经手人是谁。

过去，“这次事故是下游引起的”是一句主张。现在它是两边的链路数据摆在一起。

所以我要正面承认一件事，而且这话我四年前绝对说不出口：

禅道那几年，问题依然没有被解决，但问题已经可以被看到了。

我以前把这句话当遗憾。现在我知道它是成就。

因为它完成了一次降级：把一个“感觉”降级成一条“记录”，把一团“状况”降级成一组“条目”。

在只会奖励“解决”的评价体系里，这一步看起来最没用——你没有修好任何东西，你只是把丑事登记在册。可它是后面所有事情的前置条件。没有身份证的人，连被追捕的资格都没有。

5. 记账权不等于销账权

但这里必须停下来，把裂缝说清楚。否则这篇文章就成了自我表扬。

可见性解决的是归因成本，不解决修复权限。

我把命变成了账。可账能不能销，需要签字权。而签字权不在我手上——它属于那些有预算、有排期权、有资格说“这个季度就修这个”的人。这一环，正是我在四年复盘里写下的那条：唯一不可自控的一环是接收者（顺序比努力贵：四年复盘）。

所以“禅道推进四年、问题依然没解决”，不是我方法失效，是射程到此为止。

这一步的边界，用两个词就能划清：

  • 记账权：能不能让一件事被记下来、被查到、被对上。这个我拿到了。
  • 销账权：能不能让这件事被排进别人的日程、占掉别人的资源、动到别人的KPI。这个我没拿到。

绝大多数团队停在“记账”就不动了，不是因为不会往下走，是因为从账到销的那一步，需要有人在自己的名字下承认一笔亏损。而账本的第一个功能，往往不是催人干活，是保护那些不认账的人——这一点我在另一篇里拆过（账本失明：为什么你越做得好，越像没干啥事）。

所以准确的说法是：

让问题被看到，是把命变成账。账能不能销，你说了不算。

这句话比“解决问题的第一步是让问题被看到”更冷，但它更真。因为前者听起来像成功学，后者才是工程。

6. 这一步为什么总被跳过

既然“让问题被看到”是第一步，为什么绝大多数团队直接从“解决”开始？

因为它产出的是难堪，不是方案。

在技术人的英雄叙事里，“解决问题”是主角台词——力挽狂澜、定位根因、一夜修复。“生产问题”是什么？是把丑事摆到台面上，是把某人的疏忽、某段流程的漏洞、某个决策的代价，变成一份谁都能翻的记录。它长得像打小报告。

更要命的是定价结构：

  • 成本：立刻付、自己付、还是人际成本。你会得罪人，而且是具体的人，今天就得罪。
  • 收益：延后、公共、且很可能记到别人账上。半年后系统稳了，谁会觉得这是当年那个装探针的人的功劳？没人。因为什么都没发生。

一笔成本立刻私有、收益延后公共的买卖，在任何组织里都不会有人主动做。

于是大家直接跳到“解决”。

而他们解决的，是已经有人喊出来的那部分问题。喊得响的先修，有领导关注的先修，出过事故的先修。剩下的从不被提起——不是因为被压下去了，是因为它们从来没被生产出来过。

跳过“生产问题”这一步，你不是在解决问题，你是在解决那些已经吵起来的问题。

这就是那位同事那个产品六七年来的真实状况。不是没人管，是没有一个东西存在到值得被管。

7. 七天与四年

现在解释开头那个时间差。

他那边的客观条件，他自己都清楚：

  • 零可观测性。 没有既得利益者，不存在“我们原来那套怎么办”。
  • 从 0 到 1。 推进阻力小，没有历史的账要还。
  • 内存链路重启即清零。 出问题也只是重启一次，爆炸半径可控，最坏情况是丢几十秒数据。

这三条，恰好是 减摩擦工程：如果重来一次，我按什么顺序动手 里那条“先便宜，后价值”的完整实例：第一刀必须便宜到不需要任何人批准。

至于架构，看着是“不适合”，其实是最省钱的一种适合——这一点值得单独说一句。

伪微服务对运维是灾难，对探针却是红利：几十个服务在同一台机器、同一个网络命名空间里，调用就是 localhost:port。这意味着不需要跨机传递 trace 上下文，不需要 sidecar，不需要 OAP 集群和 ES。一个 agent 挂上去，本地落盘、内存环形缓冲，全部服务的进出就都在里面了。

真微服务反而要解决跨节点传播、采样一致性、时钟偏移三道题，他这里一道都不用做。

也正因为这台机器已经紧到随时会被 OOM Killer 砍一刀，这套东西才必须是极简的：几百 KB 的环形缓冲、本地 rollup、零外部依赖。把那套 OAP + ES 搬过来，先死的是他那个本来就没内存的产品。

技术选型从来不是审美，是架构逼出来的唯一解。这条推导的完整版在另一处（极简监控·压轴篇）。

但上面这些，全是他那边的客观条件。真正决定这件事七天能成的，还有一条，而这条是我做的：

我挑了他。

我没有去布道。我没有在部门会上讲一遍、等大家被说动、然后一个个去推。我只挑了一个人——他的产品结构刚好对着这套东西的靶心，他的痛点刚好能在一周内被证伪，他自己刚好有动手的权力。

三条齐了，不需要说服。他自己会跑。

这不是“选人比选事重要”这种鸡汤。这是我被现实教出来的降级解法：既然不能指望所有人觉悟，那就只找那个已经在等它的人。布道赌的是“我能改变别人”，筛人赌的是“有人本来就准备好了”。前一个我赌输过整整一年（那个“把结构当认知”的布道期，写在 顺序比努力贵：四年复盘 里），后一个我赌赢了。

所以真正可复制的东西，不是那套监控，是这条判据：

这个人手上有没有一个零可观测的产品？他有没有一个能在一周内被证伪的痛点？他有没有权力自己动手？

三条齐了，七天。三条不齐，四年，或者永远。

8. 把顺序调过来

所以整套东西的顺序，应该重排。

大多数方法论的开头是“如何解决问题”——找根因、拆解、闭环、复盘。这些话都对，但它们都默认了一件事：问题已经存在，就摆在那儿，等着你去解决。

而现实里，第一道关卡根本不在那儿。第一道关卡是：你能不能造出一个足够硬的东西，硬到所有人都没法再假装看不见。

三步，一步都不能跳：

  1. 让它被读到。 探针、指标、链路。这一步解决“有没有对象”。
  2. 让它被记下。 账本、时间戳、归属、次数。这一步解决“这个对象有没有历史”。
  3. 让它被销掉。 排期、资源、KPI。这一步解决“历史能不能变成行动”。

第三步不在我手上，我认了。但前两步可以单方面完成，而且必须做到底——

因为把命变成账，是你能单方面完成的最后一步。

做完这两步，你至少留下了一样别人夺不走的东西：一个无法被否认的一周。谁都可以说“最近挺稳定的”，但没有人能对着那张曲线说“上周三 10:32 没出过事”。

这就是我这个“生产问题的人”的全部产出。它不体面，不上镜，不能写进任何一份述职材料的第一页。

但它把一个本来只能靠天意的现场，变成了一个可以算账的现场。

后记

今天下午听到他往测试环境推 MVP 的时候，我脑子里冒出来的不是“这套东西真好用”，而是一个很奇怪的画面：

一个房间，黑了很多年。所有人都在里面摸索着走路，撞到东西就绕开，撞疼了就骂一句，然后继续摸。有人往墙上打了十几个手电筒的孔，光柱照进来，照到的还是自己原来撞过的那几个角。

然后有人走进去，把电灯装上了。

灯亮的那一刻，房间里的问题才成为问题。 在那之前，那些叫障碍、叫运气、叫这屋子就这样。

我这四年，没扫过一次地。我只是把灯装上了。

至于屋子要不要收拾——那不是装灯的人能决定的。

封面解读

这张封面是一个剖面式的视觉隐喻：它压住了全文最核心的那组对立——被照到的一小块，与还在黑暗里的全部。

那盏孤零零的灯泡 = 探针，也是整篇文章里唯一的光源。 它不打扫房间，不搬走任何东西，它只做一件事：让原本没有轮廓的地方第一次有了轮廓。这就是可观测性的真实身份——它不是解决方案，它是让解决方案成为可能的前提。四年前我以为自己在修东西，现在才知道我是在装灯。

光圈与黑暗之间那道渐隐的边界 = 射程。 请注意它是软的、模糊的、慢慢暗下去的，不是一刀切的黑白分界。这正好对应第 5 节那条必须承认的裂缝：可见性有半径。光圈之内，问题有名有姓、有次数、有时间戳，可以被记在账上；光圈之外，仍然是命。而账能不能销，不取决于光照得多亮，取决于有没有人愿意签字。灯的功率再大，也照不到签字权所在的屋子。

光里那堆东西 = 被判了刑的老问题。 倒扣的木凳、码着的砖、凹了的铁桶、塌了的木箱、盘成一圈的电缆、断掉的木板——都是“放了很久、没人动过、也没人扔”的东西。这正是那个产品六七年来的样子：不是没人管，是没有任何一个东西曾经存在到值得被管。直到光落下来，它们才第一次成为“东西”，而不是“这屋子就这样”。

每件物品一侧受光、一侧拖出一道短影 = 归因。 有了唯一光源，影子就有了方向；有了方向，就能反推是谁挡住了光。在没有光源的地方，同样的物件只会是一团说不清的暗。影子不是问题的副产品，影子是问题可被指认的证据。

而画面上大片大片什么都没有的黑 = 谦虚。 这张封面里，被照亮的部分大概只占六成，剩下的四成是纯粹的空。它没有假装全知，也没有假装照亮了就万事大吉。房间还在，绝大部分仍然看不见——这才是这套东西真实的覆盖率，也是我不敢把话说满的原因。

一句话总结：灯不打扫房间，灯只让房间第一次有了边界；而边界之内能不能被清扫，从来不是灯能决定的。

原始素材和基础语料（人工）

搜下我的博文库，尤其是最近二十篇，关于我最近四年的总结的。我今天在推行我的https://fulizhe.blog.csdn.net/article/details/166740106；周一给公司部门内部负责其它软件产品的同事分享了思路，他自己就依靠AI实现了一个MVP，当然这个同事是我挑选过的—— 他负责的产品的软件架构非常适合这个思路所面向的产品，他那个体系下啥也没有；而且我这个是基于内存的链路，重启即清零，所以即使有问题也是影响有限，加上他是从0到1，推进阻力小；今天下午他就开始往测试环境下推MVP了。 从这个我突然又了另外一个总结： 解决问题的第一步是让问题被看到，我这个同事他负责的产品也是公司里迭代六七年了，过往可观测性为零，解决问题完全是靠运气，运气好一下找到对应日志了，如果遇到hang住，系统慢等问题那就算了碰上硬岔子了，完全是靠天意或者是不断补日志循环，上下游跟着累吐学还不保证能解决。但有了这一套，秒级定损，因为问题点能够被第一时间看到；回看我过去这几年，尤其是禅道推进，其实依然没解决，但问题已经可以被看到了

续补（架构事实纠正，2026-10-21）：他的那个系统的架构是java 微服务，但是他的所有微服务全部部署在一台机器上，这就是我之前写过的一个概念，叫啥呢，叫伪微服务，https://fulizhe.blog.csdn.net/article/details/161136408 你学习下。他的典型特征如下：1. 性能差：因为所有服务都要部署到同一台机器上，所以同一台机器上可能会部署几十个服务，如果机器配置是 16G 内存的话，可能会有服务因为内存不足被 OOM Killer 杀掉 2. 启动顺序依赖：比如 A 服务依赖 B 服务，B 服务依赖 C 服务，C 服务启动的时候有非常耗时的操作，导致 A 服务无法启动。这样会导致 A、B、C 都无法正常工作，整个链路挂掉。
