前言

今天联调，遇到一个起不来的插件。

plugin-manager 是我们自己做的一套插件管理体系，基于 etcd 做注册中心，Java 体系。过去一年我把该配的可观测性都配上了：在线日志查看、在线环境变量、在线插件管理，以及基于 skywalking-local 的链路追踪——请求先到 plugin-manager，再分发到各个 plugin。

这些配置不是临时给 plugin-manager 加的东西，是我这些年一点点攒出来的同一套能力：最近两年一直在线上被反复验证，我向领导报出去的指标只有一个——故障定位，五分钟以内。

先把三方关系摆清楚，后面不再重复：plugin-manager 是我们团队做的系统，它的负责人——也就是负责插件生命周期的那个开发负责人，后文统一称”插件负责人”；plugin 是别人的模块，归各个插件开发者。 agent 是插件负责人配的——每个 plugin 的启动参数里都写进了 skywalking agent。

然后联调时，某个 plugin 启动之后，始终连不上 etcd。日志里刷的只有两条 WARN，间隔十秒，反复重试：

先把话说在前面：这类问题我们过往已经解决过，不是解决不了。这篇文章不是讲它怎么修的。

1. 两行没有堆栈的 WARN

这两行日志我念一遍，因为它本身就是证据。

第一，没有堆栈。 IllegalStateException 被业务代码 catch 住，然后用 log.warn(e.getMessage()) 打了出来——异常对象没传进 logger，堆栈自然就丢了。一个能让插件注册失败的异常，只留下了半句话。

第二，没有 error。 整个启动过程里，error.log 从头到尾是空的。

一个插件起不来，一个能炸掉注册流程的异常，在这套日志体系里连”错误”都算不上：只配一条 WARN，而且这条 WARN 是残缺的。

不看别的，就看这一件事。

2. 第一次上赶着：我给建议，插件负责人要 traceId

看到这个现象，我没等人问，先把建议递了过去。这是文中第一次”上赶着”——插件负责人没开口，我先开了口。

我给建议的对象是插件负责人。agent 是插件负责人配的；plugin 是别人的模块，插件开发者只写插件，不配这些。

建议本身很直接：把 skywalking agent 只配到 plugin-manager 上，各个 plugin 不要管。

理由也直接。链路的起点在 plugin-manager——请求先到它，再由它分发出去，进来出去的时间戳它这里都有。plugin 是插件开发者的模块，它自己的可观测性，该由插件开发者自己负责。

插件负责人的回复是：希望到时候通过一个 traceId，把整条链路串起来。

这句话单独听，是对的。全链路追踪是业界标配，一条 traceId 从入口贯到最后一个节点，谁看都专业。

问题不在它对不对，在它是谁来付。

链路串起来，要 N 个插件都挂 agent。插件负责人要的，只是每个 plugin 的启动参数里加一行——可这一行加进的是插件开发者的模块。 这一行加上去，成本就从插件开发者那侧，挪到了 plugin-manager 团队这侧：N 个 agent 的安装、升级、版本兼容、日志噪音、误报，以及刚才那种把插件启动搞挂的故障，全落在这儿——落在我们这边。

这笔账得说公道点：插件负责人不是来白拿的。 这套东西他跟了整整一年才接受——他肯付这一年，是因为他有机会用，并且真的用出了好处。他和那些插件开发者唯一的差别，也就在这儿：插件开发者没这个机会。

而这恰恰是不能替插件负责人垫付那 N 份配置的理由。接受一件事本身是有成本的，一年都不算长。

上赶着还有第二重意思：替插件开发者把学费也交了。 人教人教不会，事教人才教得会——插件负责人那一年的转变，不是谁劝出来的，是自己吃过亏、又尝到甜头之后一点点认下的。你把这笔学费抹掉，就等于抹掉了插件负责人唯一的改进机会：他不会谢你，他连”该改”都不会知道。

再往前一步说：链路的形状，不等于链路的作用。 形状是一条贯通的线，作用是从线上读到东西。可 agent 加进的那些模块，error.log 里连一条记录都没有——串起来，也是串了个空壳。

把这条要求翻成买卖的语言，底就露了：那 N 份配置不是合作，是替插件开发者出价。跳过插件开发者出价那一步的给予，就是赠品。

我能做，只是不打算替插件负责人做。 赠品这东西，送出去的那一刻就开始贬值。

3. 这两行日志只证明一件事

我不打算从这两行日志里推出什么普适的方法论。它只证明一件事：

插件开发者不在乎可观测性，也不在乎效率。

而且不是”他们懒”，也不是”他们坏”——是插件开发者所处的位置决定了这件事与他们无关。 我在另一篇里拆开过这类人（从消费者到投资者）：消费者心态——消费者不需要为消费体验之外的结果负责。 插件开发者进了这个系统，买的是八小时的服务体验；效率是别人的效率，不是他们的消费体验。

这一点得跟前一句公道话并排看：插件负责人不是这一类人。 他跟了整整一年才接受，是真的在用。区别也简单——插件负责人有机会用，插件开发者没有。

把这件事的账拆开，一共三段，每段都落在同一边：

第一，成本是真的，而且全在我们这侧。 替插件开发者的模块配上的 N 个 agent，安装、升级、版本兼容、日志噪音、误报，以及刚才那种把插件启动直接搞挂的故障——这些不是纸面成本，是每天要有人收拾的东西。收拾的人是我们，不是插件开发者。

第二，对端是空的。 付出之后，对面没有接收方。证据就在眼前：一个能让插件起不来的异常，在插件开发者那里不求有堆栈，甚至不配当 error。一个连自己那一侧的日志都不看的插件开发者，你给他铺一整条链路，他会拿它做什么？

第三，回报从来没有被承诺过，而且不会被承诺。 形状与作用的区别，前面已经说过，这里只补一句：链路串起来，是给汇报交差的形状；等真要排错那天，那些模块里没有东西可读——形状到位了，作用还是空的。

三段账合起来只有一个结论：这不是合作，是我们单方面补贴。

只交手一次，让利还能算人情；要反复交手的局里，让利就是一份稳定的抽成。《合作的进化》里那场反复博弈的锦标赛，结论也很朴素：赢的不是最善良的那个，是善良但会还手的那个。

所以绳子的答案很清楚。

我在另一篇里写过（先在岸上：可观测性不是护甲，是善行的资格线）：想上来的，我手边有绳子。今天要补半句——手都没抬的人，绳子不必送过去。

插件开发者连手都没抬：他们没配过链路，没打过一条 error，也没开口要过任何东西。伸手的人愿意自己握；插件开发者根本没伸手——只是插件负责人想把绳子替他们塞过去。

插件开发者不在乎的东西，我更没有理由替他们放在心上，更不必上赶着塞过去。

4. 出界的那一跨

这里有一个技术细节，我想顺手记下来，因为它和组织上的事长得太像了。

SkyWalking 的 span 模型里，有一类叫 exit span——出界的那一跨：从我这个节点，走到别人那里去。这个模型有一条硬规定：exit span 必须带 peer，也就是对端是谁。

为什么？因为”出界”这个动作，天然要求一个明确的对象。你要走到谁那里去，你得知道那是谁。没有对端，这一跨连生成都生成不了——所以它抛了 Exit span doesn't include meaningful peer information。

组织上是同一个道理：越界协作，必须有一个明确的责任主体。 对面没有一个认账的人，你伸过去的手就没有落点，你付出的在乎就没有接收方。技术上是 IllegalStateException，组织上就是你替人白干。

这个异常我只当类比，不往下推演。但这句话我确实喜欢——

出界的那一跨，需要一个明确的对端。

再往前半步，就是标题的第二个支点：投给一个没有对端的人，那不叫投资，叫沉没。

5. 顾好你自己

给出我的结论，就三句。

第一，agent 配到自己的边界为止，配到底，一寸不多。 plugin-manager 里的日志、环境变量、插件管理、链路追踪，一样不能少，而且要能让任何一个人随手取用——这才叫系统属性，不是我自己的绝活。

这一寸不是白来的：它是这些年攒出来的同一套能力，近两年在线上被反复验证过，压得住”故障定位五分钟以内”这个指标。所以”我能做但不打算替插件负责人做”不是逞能——这是一份有凭据的资产，而资产只投在有对端的账上。

第二，出问题的时候，第一时间把边界条件摆出来，而不是先动手。 这不是消极。先把”我这侧是什么状态、边界在哪、证据是什么”摆清楚，再谈插件开发者那侧。顺序反过来，你就从旁观者变成了施工队。

第三，不慌、不抢着查、不主动认领。 插件起不来是插件的事，链路断在插件开发者那一段是插件开发者的事。我可以告诉你现象在哪、日志在哪、边界在哪——我可以把工具给你，但我不替你握着。

说得再难听一点：插件开发者自己在泥坑里滚，我不进去，也不递绳子。

后记

这件事本身很小，小到如果不是那两行日志太典型，我大概不会写它。

但它让我把一句话想得更硬了一点。过去我说”先在岸上”，落点在”我得上岸”。今天这个插件告诉我，岸上之后还有第二层功课——分清谁在伸手，谁在看戏。

绳子只有一根。给错了人，你就得下水。

封面解读

这张封面只压缩了一个判断：你照亮你自己负责的那一段路，多一寸都不必。

贯穿画面的那一条路 = 同一件事、同一个系统。 它不是两条并排的路，就是一条，从近处一直延伸到远处。这一点很重要——插件开发者不是”另一个世界”，他们跟你在同一件事里，只是站在路的后半段。

横切路面的那道亮线 = 责任边界。 它清晰、笔直、不含糊。整幅画里唯一需要被看清的东西就是它。

下截（我这边）：整段通亮，网格清晰，数据节点全亮，三根探针柱立在路上。 探针不是立在画面之外，是立在自己这段路上——这就是”配到自己的边界为止，配到底”。

上截（插件开发者那边）：同一条路的延续，同样的宽度、同样的网格，但全暗。 注意它不是虚空，它有路面、有结构，只是没有一盏灯、没有一根探针、看不到任何测量。这正是”插件开发者不在乎”的准确画法——不是没有系统，是没人测量。

光严格停在边界上，一丝都没有溢上去。 这一笔对应的就是第 5 节那三个字：一寸不多——资产投到哪，灯亮到哪，多一寸都不投。

一句话：路是共用的，灯是自己点的；点到自己这段路的尽头就够了。

原始素材和基础语料（人工）

今天遇到了这样一个现象，依然是有关于可观测性 + 团队管理的。我们自身做了一个 plugin-manager 系统，基于 etcd 注册中心做的 plugin 管理体系，Java 语言体系下；在参考过往的成熟经验引入了必要的可观测性方案——在线日志查看、在线环境变量、在线插件管理，基于 skywalking-local 的链路追踪（请求先到 plugin-manager，然后到各个 plugin）。相应的开发负责人负责了插件生命周期，所以将 skywalking agent 配置到了每个插件的启动参数下。联调时发现某个 plugin 启动时始终无法连接 etcd，通过在线日志浏览发现其日志打印：

[-registry-guard] c.kanq.bigdata.gridflow.registry.EtcdRegistryGuard : ### [guard] 建立 etcd 注册表 watch 失败: java.lang.IllegalStateException: Exit span doesn't include meaningful peer information.

[-registry-guard] c.kanq.bigdata.gridflow.registry.EtcdRegistryGuard : ### [guard] 注册巡检失败: java.util.concurrent.ExecutionException: java.lang.IllegalStateException: Exit span doesn't include meaningful peer information.

我给负责人的建议是：你让整个 skywalking agent 只配置到自己的 plugin-manager 上，各个 plugin 不要管。负责人给我的回复是：他希望到时候通过一个 traceId 能够把整条链路串起来。我的回答：你看他这个日志输出，错误连堆栈信息都不输出，这像对于效率有追求的吗？你顾好你自己就行了，出问题的时候第一时间把边界条件摆出来，让他们自己去泥坑里滚，确保自己不沾身就行了。

（续补）这个问题我们已经解决了。补充一下：对方压根没输出 error 日志，error.log 里是空的——目的和前面那行日志是一样的，说明对方并不在乎可观测性，不在乎效率，这些背景只是为了验证这个人或者说 plugin 提供方不值得扔绳子，让他们自己去滚泥坑。

（续补）不是”技术上越不过去”，是对方都不在乎，我们更应该不在乎。

（续补）这个倒不至于，这个人也是看到我这套理念以及实际好处之后才参与进来的，他和那些插件开发者的唯一区别是他有机会使用到并感受了这些可观测性的好处，他自己也是花费一年才接受的。

（续补）人教认教不会，只有事情教认，吃了亏了才能有改进。这也是上赶着的另外一个说法。

续补记录（与正文改动一一对应）：

  • 标题由初始的《对方不在乎，我凭什么在乎》改为《对方不在乎，我自然更不应该在乎》。
  • 前言收尾由”这件事我们后来解决了”改为”这类问题我们过往已经解决过”——后者说的是能力早就在，前者暗示为本次专门投入，会削弱”能做但不做”这个论断。
  • error.log 空白最初被处理成独立的第二层证据（并一度拟作题眼），后按用户意见并入第 1 节，与”不打堆栈的 WARN”并列，只承担”同一论据的第二个样本”这一个作用。
  • 原第 4、5 节（”素养探针”式的判断标准）被删除——把已经判定的结论重新包装成待研究的方法论属于拔高；素材的功能只是验证该 plugin 提供方不值得扔绳子。
  • 第 3 节收尾句”对方不在乎的东西，我更没有理由替他放在心上”为标题点题句。
  • 封面从”两条平行路”改为”一条路被横向边界分成两截”，并去掉画面上全部文字。

（后续修订）

  • 标题再由《对方不在乎，我自然更不应该在乎》改为《手都没抬的人，绳子不必送过去》。取正文第 3 节自己的金句作题：原标题是”因果+辩白”结构，「自然应该」在替自己找理由；改用”绳子”意象后，标题自带画面和钩子，也承接《护甲到资格线》那篇的绳子线索。第 3 节收尾句”对方不在乎的东西，我更没有理由替他放在心上”从题眼退为普通收束，不再承担标题功能。
  • 文件名 devops-they-dont-care-so-why-should-i.md 保持不动——permalink 为 :year/:month/:day/:title/，:title 取文件名 slug，改文件名就会改掉文章 URL，发布后再改即断链。首版提交 4304883 已推送上线，本次修订承接其后。

（第三次修订：标题定型）

  • 标题最终定为《上赶着不是买卖：探针是资产，不是赠品》。放弃”绳子”意象作题——绳子那段画面归位到正文第 3 节，标题改用”俗语钩子 + 产权定性”两段式：前半是民间直觉（上赶着不是买卖），后半是可观测性侧的落点（探针是资产，不是赠品）。
  • 定题依据（用户意图，分四层递进）：① 上赶着不是买卖（民间直觉，基础）→ ② 《合作的进化》反复博弈（给出”为什么”）→ ③ 人性的弱点（给出机制）→ ④ 管理学基本理念（给出规范）。标题承载 ① 与 ④ 的落点，② ③ 由正文承担。
  • 落点在可观测性体系（用户核心专题：多年自建、近两年验证有效、已向领导承诺故障定位五分钟内）。管理与人际常识只作引子，不越位成主体。
  • 遗留：正文尚无”多年建成 / 两年验证 / 五分钟定位”这三项资产凭据，亦无”上赶着”这一被否定的动作；与”资产/赠品”定性配套的正文修订待办。

（第三次修订：正文跟进，衍展不覆盖）

  • 指代纠正：文中”他”自始至终指 plugin-manager 的负责人（即插件生命周期的负责人），不是插件开发者。前言原句”他们给每个 plugin 都挂上了 skywalking agent”易被误读为插件作者所挂，已改为”agent 挂在哪个 plugin 上，是他那侧定的……跟插件作者无关”。§2 现明确”我给建议的对象是 plugin-manager 的那位负责人”。
  • 「上赶着」落地：§2 节号改为”第一次上赶着：我给建议，他要 traceId”，并点明”我没等人问，先把建议递了过去”就是一次上赶着；§3 收尾补”更不必上赶着塞过去”，标题的”上赶着”在正文有了对应的动作与判词。
  • 「资产」落地：前言新增第三段（这套能力是多年攒成、近两年线上反复验证、向领导报的指标是”故障定位五分钟以内”）；§5 第一条把”配到底”改为”配到底，一寸不多”，并补”这是一份有凭据的资产，资产只投在有对端的账上”。
  • 「赠品」落地：§2 增”他要的不是合作，是一份赠品——一份他自己没投过一分钱、也不用为后果负责的东西”，并接”赠品这东西，送出去的那一刻就开始贬值”。
  • §3 由 5 行扩为机制论证（三段账：成本归我 / 对端为空 / 回报未被承诺 → 单方面补贴）。扩写严格限制在”服务于本次判定”的范围内，未新增独立章节，未展开成方法论讲义——对齐旧记录中”把已判定的结论重新包装成待研究的方法论属于拔高”这一原则。博弈论仅一句（《合作的进化》锦标赛：赢的是善良但会还手的那个）。
  • 「消费者心态」入正文：§3 引用 从消费者到投资者，作为”他为何不负责”的机制解释；该篇已加入文末「相关」。
  • §4 在题眼句后补”投给一个没有对端的人，那不叫投资，叫沉没”。
  • 修 bug：封面解读原句”这一笔对应的是最后那三个字：一寸不多”，正文中并无”一寸不多”三字（悬空引用），现正文 §5 已补该三字，封面解读相应改为”第 5 节那三个字”。
  • 封面未重画——“照亮自己那一段路，多一寸都不必”与”探针是资产，只投在自己这段路”兼容。
  • 「相关」由 5 条变 6 条（新增消费者心态一篇），如要维持 Top 5 惯例，可自行砍一条。

（第四次修订：三方关系订正）

  • 人物关系定稿（三方，非两方）：
    • 「我们」= plugin-manager 团队（我方，也是全文叙述者”我”所属的一侧）；
    • 「他」= plugin-manager 的负责人（与我方同队，agent 是他配的）；
    • 对应方 = 各个插件开发者（plugin 是别人的模块）。
  • 前言据此刻意加了一句”先把三方关系摆清楚”，把三方一次性交代完，后文不再重复；MindMap 的 C 分支由 3 项扩为 5 项（agent 是他配的 / plugin 是别人的模块 / N 个 agent 的成本归我方团队 / 一条 traceId 的叙事归他 / 能做不等于该做）。
  • 成本归属句定稿：成本不是”我个人”的，是”从插件开发者那侧挪到了 plugin-manager 团队这侧“。§2、§3 相应措辞统一为”我们这侧””收拾的人是我们，不是插件开发者”。
  • 删掉 §2 与 §3 之间”形状/作用”的整段重复表述，§3 第三段账改为回指前文。
  • “赠品”的定义由”他没投过一分钱”改为”他没建过、也不打算维护“——agent 确实是他配的（他投了一行），但可观测性这套能力他没建过也不维护，这才是赠品的准确含义。

（第五次修订：给”他”平反）

  • 删掉”他白得一条能拿去汇报的 traceId”这一判断。 事实相反：这套可观测性他跟了整整一年才接受；他肯付这一年，是因为他有机会用、并且真的用出了好处。他和那些插件开发者唯一的差别就在这儿——他们没这个机会。把他归入”白拿”，是把入局者错当成了搭便车的人。
  • 因此 §2 的账改成两头都说清：成本从插件开发者那侧挪到我们这侧；而”不接受”这件事的原因也摆在插件那侧。所以那 N 份配置的本质是替别人出价——跳过对方出价那一步的给予，才是赠品。
  • 「他真正想要的是链路的形状，不是链路的作用（形状是给汇报看的）」一句属于对动机的推断，一并改掉，只留事实：链路的形状不等于链路的作用；他加 agent 的那些模块 error.log 里连一条记录都没有，串起来也是空壳。
  • MindMap 的 C 分支把”一条 traceId 的叙事归他”换成”他花一年才接受，不是白拿“，并新增”形状 ≠ 作用：模块里没有日志”。
  • 「赠品」定义再度收紧：由”他没建过、也不打算维护”改为”替别人出价“。

（第五次修订补记：上赶着的第二重定义）

  • 新增一层机制，来自用户原话”人教人教不会，只有事情教人，吃了亏了才能有改进。这也是上赶着的另外一个说法”（原话已按惯例收入「原始素材」节）：
    • 上赶着赔的不只是钱，是替对方把学费也交了。 他那一年的转变不是劝出来的，是自己吃亏之后认下的；替别人免掉这笔学费，等于同时免掉他唯一的改进机会。
    • MindMap 的 C 分支相应新增”上赶着 = 替对方交学费”。
  • 这一层同时回答了”为什么垫付一定无效”：不是对方这次没接，是垫付这个动作本身就消灭了对方改变的前提。

（第六次修订：§3 主语归位）

  • 经与作者确认，§3 里”不在乎可观测性、也不在乎效率”的人是插件那一侧，不是他。此前整节挂在”他”身上，与第五次修订给他的平反直接矛盾。现改为：
    • 短句判词改为”插件那一侧不在乎可观测性，也不在乎效率“；”不是他懒/他坏”改为”不是他们懒/他们坏……是他们所处的位置”。
    • 消费者心态归位到插件开发者（他们进系统买的是八小时的服务体验，效率是别人的效率）。
    • §3 新增一段专门把他摘出来：”这一点得跟前一句公道话并排看：他不是这一类人。 他跟了整整一年才接受，是真的在用。区别也简单——他有机会用，他们没有。“
    • 三段账的”他”全部改为”他们/那些模块”；第三段账不再落在”他拿形状去汇报”，改为落在空壳事实：”形状到位了，作用还是空的。”
    • 绳子段重写：原”他不是在伸手，他是在要服务”句已删（那句把他说成了索要服务的人）；改为”插件那一侧连手都没抬……伸手的人愿意自己握；这些人根本没伸手——只是有人想把绳子替他们塞过去”。
  • MindMap 的 D 分支由 4 项扩为 5 项，新增”他不是这一类：跟了一年才接受”。
  • “手都没抬的人”的所指一并确认 = 插件那一侧（与 §3 主语同一批人）。

（第七次修订：全文代词显式化）

  • 起因：第六次修订之后，”他”（= 插件负责人，与”我”同队）与”他们／对方”（= 插件开发者，对应方）在同一段内交替出现，读者无从判断当前主语。§3 与「封面解读」受影响最重——封面解读原句”对方不是另一个世界，他跟你在同一件事里”里的”他”实际指插件开发者，与全文定稿的”他 = 插件负责人”直接冲突。
  • 处置：指插件负责人的一律显式写”插件负责人“，指插件作者的一律显式写”插件开发者“；原”插件那一侧””对方””别人”一并统一。前言首次出现处补全称界定：plugin-manager 的负责人——也就是负责插件生命周期的那个开发负责人。
  • 保留代词的情形：同一段内已显式点明主语后的连续指代（如 §2”插件负责人不是来白拿的。这套东西他跟了整整一年才接受”）；以及泛指读者的”你”。
  • MindMap 同步：C4、C5、D1、D4 四处节点一并显式化。
  • 「原始素材和基础语料（人工）」一节保持原文不动；「续补记录」中的历史引用亦保持原样，不随正文改写。
  • 顺便订正一处旧记录失准：第四次修订记录称”前言原句已改为『agent 挂在哪个 plugin 上，是他那侧定的……跟插件作者无关』”，但正文实际落的是”agent 是插件负责人配的——每个 plugin 的启动参数里都写进了 skywalking agent”（第五次修订时重写所致）。记录与正文不符，特此标注，以免日后回看时误以为正文中存在该句。
