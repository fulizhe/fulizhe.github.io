前言

这个专栏已经更了二十多篇，但一直缺一个把立场说清楚的地方。补上。

先把话说死：它不教你搭一套更省钱的 Prometheus，也不论证「轻量」比「重型」更优雅。它只回答一个前置问题——在单体应用里，监控究竟在哪个时刻被真正用到？

这个问题不回答，后面所有的技术选型都是在给伪需求买单。

1. 真正出场的，只有三件事

跟一线打交道久了会发现，监控被打开的时刻翻来覆去就那么三种：

一是报错。接口报 500，日志里翻不到原因，需要一个地方看清完整调用链、入参出参、异常栈。

二是卡顿。系统变慢，页面转圈，但没人知道慢在哪一环——数据库慢查、连接池耗尽、还是 GC 在拖后腿。

三是联调。上下游对不上，需要一次看清请求走到哪一步、落在哪个节点、返回了什么。

除此之外的场景，基本没有出场机会。长期历史数据挖掘、系统隐藏漏洞的提前发现、容量评估与趋势预测——这些词在大厂方案里闪闪发光，在单体应用里绝大多数时间躺在文档里睡觉。

原因不复杂：单体的性能问题通常有明确的触发路径，出了事照着现场查即可，不必靠几个月的曲线去「预警」一个还没发生的猜想。为不会到来的需求预置能力，是工程上最昂贵的一种浪费。

《庄子》说「鹪鹩巢于深林，不过一枝；偃鼠饮河，不过满腹」——需求就这么大，别按大厂的水量给自己修水库。

2. 单体没有为监控申请资源的资格

第二层约束更硬：单体应用资源少。

一台机器、两个 G 堆就是常态；ToG 交付现场给你一台内网虚拟机已经算客气。在这种前提下，去申请一整套独立资源部署监控——Prometheus 加存储、Grafana、SkyWalking OAP、Elasticsearch——机器从哪来？运维谁做？

现实答案通常是：申请不下来；或者申请下来了，也没人肯长期维护。于是它从立项那天起就走不完，更别说活到下一次事故。这意味着很多人不愿承认的事：重型方案在单体场景里不是「贵」，而是「不存在」。 你没法用一套不存在的系统去排障。

3. 依附于应用本身，jar 依赖不是妥协

独立部署走不通，方向就只剩一个：让监控依附于应用本身，以 jar 依赖的形式引入。

它常被挑剔的是「生命周期一致」——应用一挂，监控跟着一起挂。但把这件事想透，会发现这根本不是缺陷。应用都不在了，你监控什么？反倒是「同生共死」这个特性，把三件最麻烦的事一次性免掉：不用申请机器，它跟着应用一起部署；不用单独运维，它没有独立进程；不用走审批，它就是 pom.xml 里的一行依赖。

换来的是零运维成本。而它真正的收益比省钱值钱得多——它能破冰，也能把效率直接兑现在故障现场。

4. 效率：把三天的口水战压成一分钟定责

业务场景里没有什么高深的技术问题。单体应用的故障，绝大多数不是分布式一致性、不是算法复杂度，而是配置写错、SQL 少个条件、连接池漏了、某人改了字段没通知下游——都在常识范围内，不需要博士学历去定位。

真正贵的不是技术难度，是时间。一个典型的线上问题长这样：业务方说「页面卡」，后端说「我接口很快」，DBA 说「SQL 没问题」，运维说「机器正常」……每一方都能自证清白，因为每一方手里只有自己那一段的数据。问题于是在群里拉锯两三天，最后靠嗓门大小和加班时长决定谁背锅。人的精力本该花在做事上，却全耗在自证清白上。

监控在这个场景里的价值，就是把每一段证据一次摊开：请求从哪进来、经过哪几个环节、每环耗时多少、参数是什么、异常在哪一层抛出。三天变成一分钟。 定责不靠嗓门，靠数据——这一对关系我在另一篇里拆过（可观测性等于效率）。

5. 便捷性：排错为什么要登录服务器？

先说清楚：这一整套东西，发明不在我这里。

Oshi 是现成的，Micrometer 是 Spring Boot 自带的，Actuator 你早就依赖了，SkyWalking、Jolokia、Druid、JavaMelody、Glowroot 全是别人的作品。我所做的绝大部分，是把它们集成起来，集中展示，做可视化。

这两件事各有一份价值。

  1. 集中展示，解决的是孤证不立。 单个数据源给出的永远只是一个可疑的片段——日志说超时，监控说 CPU 正常，SQL 说这条查询跑了三秒。分开看，每一条都能被解释掉；摆在一起做交叉验证，才拼成无法抵赖的证据链。

  2. 可视化，把破冰的可能性拉到极致。 命令行里的原始数据，只有熟练的人能读懂；一张图表摆在浏览器里，谁都能一眼看明白。看懂的人越多，愿意用的人就越多。

但有个前提必须先立住：业务场景里没有技术难题。

正因如此，要让一群研发抛弃既有习惯、转而熟悉你这套东西，理由只剩一个——便捷。除非传统手段在极端场合彻底失灵（典型如 logFileReporter 那类插件，能把 HTTP 调用的入参完整抠出来，不用它根本无从下手），其余场合的胜负手全在「便捷」二字上。

举个最朴素的例子。过去看线上日志：申请服务器权限、SSH 登录、找到日志目录、tail -f、grep 翻半天——每一步都在消耗意志力。现在一个 restful 接口，日志直接在浏览器里滚动，能按关键字筛，能框时间范围。

所以我一直主张：排错为什么要登录服务器？解决问题才是目的。

顺带说一句：这套东西我 2017 年左右就在想，直到去年才成型，中间隔了六七年。这同样是便捷性在作祟，而且是两重。

  1. 一重是现状还能用——当旧办法没让人痛到无法忍受，任何「更方便」的东西都很难让人动心，包括我自己。

  2. 另一重更扎心：采集到的数据不直观，可视化全靠我自己那点微薄的前端 html + js 手艺硬扛，进展慢得像蜗牛爬。想法早就有了，可每次动手都要从头造一遍轮子，热情磨没了，也就搁下了。直到 AI 出场——同样一张图表，现在五分钟就能出来。

这才是便捷性的完整含义：它不只是让使用者少登录一次服务器，也是让创造者终于能把想法变成交付物。 前者决定别人愿不愿意用，后者决定你有没有可能做得出来。

6. 破冰的前提：别指望人主动

效率这么值钱，为什么还是推不动？

因为大多数人进职场，姿态是「消费」。C 端人格（这个概念出自 从消费者到投资者）——他们不是带着「我要让这件事更高效」的 owner 心态，而是「我买了八小时服务体验」的消费者心态。效率是老板操心的事，把这八小时熬完就够了。

这不是道德问题，是经济学。效率提升的收益归老板，成本归自己；做得越快，等来的往往不是回报而是更多任务。在这种激励结构下，「多做多错、不做不错」是绝对理性。

所以推监控这件事，不能建立在「人会主动」这个假设上。你得让他第一次出事的时候，用一次、三分钟拿到答案，然后他自己会回来。这就是为什么形态必须是「极简 + 依附」：安装成本是一行依赖，使用成本是一次点击，才可能穿透 C 端人格的默认防御。任何需要先投入两星期学习、再申请机器、再等审批的方案，在它面前活不过第一周。

破冰靠的不是说服，是让效果自己说话。

后记

一年前决定把这件事做到底时，有人问我值不值得——没有收益、不参与考核、还要自掏时间。

现在专栏写了二十多篇，答案也清楚了：它不是一座高塔，是一把随身带的螺丝刀。 你不需要一台起重机，你只需要一个能立刻上手、随手可用的东西。这两者之间差的不是预算，是一个正确的起点。

封面解读

这张封面是一组体量对置的视觉隐喻：左边那点微弱的光，和右边那座庞大而沉默的黑——中间没有任何东西连着。

发光的方块 = 依附于应用本身的那套监控。 它是画面里唯一锐利、唯一亮着的东西，体积很小，却通体经络发光。嵌在正面的三枚圆形仪表，对应第 1 节的三个场景——报错、卡顿、联调，不多不少，正好三个。它没有多余的表盘，因为其余需求压根没有出场机会。

与方块融为一体的胶囊模块 = jar 依赖的形态。 它不是被摆在旁边的，而是像器官一样长在方块侧面，靠同一条发光的回路供电。这正是「生命周期一致」的视觉翻译——同生共死不是缺陷，是同一条血管。它免掉了申请、免掉了运维、免掉了审批，所以它才活得下来。

右后方虚化的庞大战架 = 那套申请不下来的重型体系。 四台机柜、积满灰、指针归零、屏幕全黑。最关键的一处细节是：它和方块之间没有任何一根线。 这不是「它不好用」，而是「它根本接不上」——在单体的资源现实里，它从立项那天起就已经死了，只是还立在那里。

左锐右虚的景深 = 极简与过度设计的分野。 画面把清晰度全给了小的那一侧，把模糊留给了大的那一侧。大面积留白不是空，是在说：能活下来的监控，占的地方本来就不该大。

一句话总结：发光的方块和积灰的机架之间没有一根线连着——能让监控活下来的，从来不是它多强大，而是它离应用有多近。

原始素材和基础语料（人工）

我写的一个专栏（「极简监控体系」，CSDN 共 25 篇）的开篇之作，现在想给这个专栏做一份介绍。我的核心观点是：对于绝大部分场景，尤其是 ToG 场景下的单体应用，监控的主要功效，是能够自下而上推进的——让一线人员看到好处，主动推广。它使用的场景主要是三个：一是出现错误，二是系统卡顿，三是联调。至于什么 metrics 之下的长期历史数据挖掘、系统隐藏的漏洞、容量评估等等，没有出场机会。而且单体应用资源少，不可能为了它再去申请一套单独的资源来部署整体监控体系。最好的监控是依附于应用本身，作为 jar 依赖的形式引入，这样虽然会生命周期一致，但能够破冰。

还有一点：效率。业务场景下没有什么高深的技术问题，这里的监控更多是属于提高效率——将原本需要两三天反复拉扯的口水战、拉锯战，缩短为一分钟内的快速定责。人的精力应该被用在它该用的位置。不过按照我博文里「消费者心态」那篇的说法，大部分人都是来消费的，磨完这八小时就行。

关于这个话题，其实还有一个关键性的特性：便捷性。我所做的这一系列集成，其实绝大部分都是以已有成熟功能为基础，做了个集成，集中展示和可视化。集中展示能够实现对于问题的交叉验证，增强证据的说服力，后者则是将破冰的可能性拉到极致。我早在 17 年左右就开始思考了，至少直到去年才成型，这也便捷性作祟，正如前面所说过的：业务场景下没有技术难题，所以让这帮研发抛弃既有习惯，转而熟悉你这一套，除了极端情况下传统手段无法定位问题，我这一套可以解决（最典型的就是我的 logfilereporter plugin），其它的则主要就是便捷性了，典型例如之前需要登录服务器才能看日志，但现在我们通过一个简单的 restful 接口，将日志通过浏览器方式展示，我也一贯主张，排错为什么要登录服务器！解决问题才是目的。

【新增第 5 节】「便捷性」独立成节，置于效率之后、破冰之前：① 先立住「整套方案的本质是集成，不是自研」——Oshi / Micrometer / Actuator / SkyWalking / Jolokia / Druid / JavaMelody / Glowroot 全是现成能力；② 集成带来两份价值：集中展示 → 交叉验证（孤证不立），可视化 → 破冰的可能性拉满；③ 由「业务场景里没有技术难题」推出「便捷是唯一的推广理由」，仅极端失灵场合（logFileReporter 类插件）除外；④ 以免登录服务器看日志为最朴素的例证，落到「排错为什么要登录服务器？解决问题才是目的」。
【第 5 节末段：便捷性作祟的两重原因（用户追加口径）】⑤ 承认 2017 年即有想法、去年才成型，并归结为两重阻力：一是现状还能用，缺乏改变的痛感；二是采集数据不直观，可视化全靠自己手写 html + js，进展极慢，直到 AI 出现才做到「五分钟出一张图」。末尾据此把便捷性推至创造者侧——它既决定别人愿不愿意用，也决定你有没有可能做得出来。
