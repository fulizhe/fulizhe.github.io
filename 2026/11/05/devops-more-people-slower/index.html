越加人，越慢

2026-11-05T02:20:00.000Z2026-11-14T11:47:46.223ZChina

前言

一段群聊，三句话：

前端：BUG 太多，改不过来了。

产品：归根结底，前期做的时候考虑太少了。

开发：现在项目要验收，客户测试人员又多，问题层出不穷。

三句话，三个方向，没有一句指向“我怎么让它不再发生”。

我盯着中间那句看了很久——不是“开发觉得是测试太多”，是有人替他们把这层意思说了出来：问题之所以暴露，是因为测试得太狠。

这句话不是气话。气话会散，它不会。它能在这个行业里传这么多年，说明它是一个世界观：世界本来是好的，是测试把它弄坏了。

顺着这句话往下走，会走到一个比 BUG 更硬的地方：慢不是因为做错了什么，是因为没有人说得清是谁做的。这篇写的就是那段“说不清”的距离——以及走到尽头之后，一个人还能拿什么交账。

1. 三种说法，一个动作

把这几句话摆在一起，会看到一件比 BUG 更有意思的事。

说法 归因落在 谁付账
BUG 是因为测试太多 测试环节的强度 测试
问题频发是因为人少、待遇低 编制与薪酬 公司
前期考虑太少 时间与经验 过去

三句话看起来在互相甩锅，其实是同一个动作：把原因挪到自己够不着的地方。

挪到够不着的地方有一个好处：不用改。也有一个代价：从此对这件事免疫于改进。

我不太喜欢用“态度”这个词，因为它不可证伪，说出来就成了指责。所以我换一个可观测的判据：

看一个人是不是真想解决问题，只需要看他的归因落在哪一格。

落在自己够得着的格子里，哪怕结论是错的，也有救——他会试，试了会改。落在够不着的格子里，哪怕结论是对的，也白搭——他从此只能等别人变。

“BUG 是因为测试太多”这句话，最狠的地方不在于它错，在于它把唯一一个能立刻变快的变量，宣布为不可动。

2. toG 没有算法与架构难题，只有定位难题

这句话说出来大概会挨骂。但我在这行待得够久，可以把它说完。

先看 toG 的系统长什么样：技术栈不深，SpringBoot 加 Undertow，没有服务网格，没有复杂的分布式事务；并发不高，一个地市几千人，峰值撑死一个早高峰；架构不新，能跑的东西没人愿意动。

这意味着“做不出来”的情况极少。真正难的从来不是把它写出来。

难的是另一件事：它横跨四种语言。前端到 Java，Java 到 Go，Go 到 C++。这四层属于不同的人，有时候属于不同的公司。

再叠三个约束：内网或专网、上门部署、客户现场的数据你拿不到。于是同一个 BUG，你能看到的现象和别人能看到的现象，根本不是同一份。

一个跨层问题的时间分布，通常是这样：

阶段 花掉的时间
定位到“是哪一层” 大头
定位到“是哪一段代码” 中头
改成正确的 小头
验证它真的好了 不定，常常反复

我做过粗估：一个跨层问题，“改”只占一成，“证明不是我这层”占九成。而那九成里，没有一行代码产出。

所以这类项目的价值不在“写”，在指认。谁能让指认变快，谁就在抬高这个项目的真正上限。

这不等于这行没有硬活，只是硬活没有长在需求文档上。它长在“让一张图同时说服四种语言的人”这件事上——手艺还在，兑现的地方换了。

所谓疑难问题，难在指认，不难在解决。

3. 效率在这类项目里只有一个定义

既然难在指认，那么“效率”这个词就有了唯一解。

不是交付速度。交付速度可以靠加班和压需求做出来，做完之后你得到的是一堆没人说得清的东西——它只是把未结案的东西提前交付出去了。

是结案时间：从故障发生，到能指认“就是这里”的那一段时间。

我写过一套东西，在业务进程里 Mock 一个 OAP，把四种语言的链路拼成一张图。写完之后我在文末留了一句话：

链路图不是用来看的，是用来结案的。

那句话当时是随手写的。现在我觉得，它是整个方案的真正定位。链路图的价值不在“看”，在终止讨论——一张图摆在桌上，“不是我”这句话就说不出第二遍。

顺着这个标准回头看，过去几年做的三件事其实是同一件事：

做的事 压缩的是
本地化 Reporter 从“出问题”到“开始动手”
Mock OAP 拼链路 从“各层各说各话”到“一张图对齐”
禅道操作线上化 从“对流程有疑问”到“查得到是谁动的”

三个指标，收敛成一句话：从故障，到指认。

顺便把边界划清：我另写过 MTTC，那是需求域的反应速度，说的是“改得多快”；这里说的是故障域到定责域的收敛速度，说的是“认得出来多快”。两件事不一样，混在一起谈，两个都量不准。

4. 加人是负优化

这是本篇唯一一个我想让人记住的判断。

逻辑很短：因为结案时间才是效率，所以组织每次补人，实质都是在效率上动手。而他们补人的依据，通常是“忙不过来”——一个用在场时间计量出来的感受。

于是就有了这个循环：

定位慢 → 看起来像人不够 → 加人 → 接口面变宽、嫌疑人变多 → 定位更慢 → 看起来更像人不够

在定位是瓶颈的系统里，加人不是往瓶颈上加水，是往瓶颈的上游加压。

再算一遍更直白：结案的过程，本质是排除嫌疑。四个人，你要排四次；八个人，你要排八次。人手翻倍，产能翻倍，嫌疑人池也翻倍。而结案时间是嫌疑人数的函数，不是产能的函数。

这就是为什么有些 toG 团队越扩越慢，扩完之后每个人还更忙——忙的不是活，是确认。

我不否认加人在别处有效。在产出为瓶颈的系统里，比如功能缺口大到根本做不完，加人是线性有效的。但那不是 toG 的主要矛盾。toG 的主要矛盾是“做完了，但说不清”。

所以这一节可以收成一句话：

用人头计量效率的团队，每一次正确的招聘，都在让下一次事故更难结案。

5. 不是没有需求，是报表里没有这一栏

我曾经把一篇讲链路图的文章推荐给一位产品负责人，他毫无兴趣。

我当时的结论是：他不在乎效率。

后来我意识到这个判断错了，而且错得不轻。他不需要结案，因为他不结案。 事故追责追到 Java、Go、C++ 的时候，他不在现场。工具的价值落不到他的损益表上，他当然看不见。

但更准确的说法是：他的报表里，没有“结案时间”这一栏。

这两件事的差别很大。需求不存在，没救；度量缺失，把数摆进去就有救。

动作其实很小：挑最近三次事故，只算一个数——从故障发生，到指认责任方的时长，再拆出其中多少花在“互相确认不是我”上。

产品负责人不会去读 gRPC 的实现，但他看得懂这句话：

三次平均四小时，其中三小时二十分，花在“都不是我”。

到那时候，不需要谁去推荐，他会来问怎么把这三个小时砍掉。

说服一个组织，不要给它架构图，给它一个能进报表的数。

6. 但我打算停止布道

写到这里，本来应该接一段“如何去推动”。我不写了。

因为布道是单向成本：我付出解释、示范、被无视之后的挫败，对方付出零。这笔交易怎么算都不划算，只在一种情况下例外——对方正在流血。

《孟子》里有一句，我年轻时读不懂，现在读着有点难受：

人之患，在好为人师。

我不是说自己是师。我是说那个动作本身：把一个好东西端到一个不需要它的人面前，然后为他的不接而生气。这个动作里有一半是善意，另一半是自我确认——我在确认我比他们更懂。

而自我确认，是最贵的一种消遣。

所以我给自己立了一条规矩：只对已经提出问题的人给方案。 没提出问题的人，你给的不是方案，是噪音。

这也正好是我一个半月前写下的一句话：先有需求，才有软件。需求不在，软件就是废纸；需求不在，方案就是噪音。同一个道理，换了个位置站着而已。

7. 我留下，不是因为信，是因为在换东西

说点私人的。

有人问过我，既然这么看不上这个团队，为什么还留着。我当时的回答很难听：年纪大了跑不了，无权无势没有托底，但又不甘心。

这三句话其实是三样不同的东西，混在一个句子里，才让人绝望。

说法 它是什么 它管到哪
年纪大了跑不了 市场约束（是真的） 只管“换一家做同样的事”这一条路
无权无势没有托底 筹码结构（是真的） 不能用“我走”谈判，只能用事实谈判
不甘心 动机 唯一属于我的东西

第二行值得多说一句。没有权力的人，唯一稳定的权力来源是别人不肯干的活：把事故拆成时间戳、把操作线上化、把四层链路拼成一张图。这些活枯燥、没有功劳、没人抢。谁干了，谁在事实上不可替代。

这不是清高，这是筹码。只不过它是一种慢筹码，慢到常常让人怀疑它到底算不算筹码。

至于“不值”，我现在把它当信号，不当情绪。它在说一句话：你的能力在这套体系里的兑换价，低于你自己的定价。

信号是真的，但它只有一个正确用法——去算账，不是去要判决书。

两笔账：

  • 留下这段时间，我换到了什么？钱、稳定、时间、案例，还是某个只有在这里才拿得到的位置。
  • 我为它付了什么？情绪、被磨掉的标准、和这些人周旋的耐心。

第一笔还有货，留下就是一笔交易，谈不上值不值。第一笔空了，那是“走”的问题，不是“说服”的问题。这两件事的解法完全相反。

而最耗人的地方，往往不在他们不行，在“我明明能更好，却被困在这里”这个叙事本身。它带一点道德上的舒服，但它是消耗品。用久了会上瘾——只要他们继续不行，我就继续是对的，也就可以继续不动作。

承认“我是自己选择留下的，为了某个东西”，不值的感觉会掉一半。剩下那一半，才是该去谈价、或者该换地方的部分。

8. 留证据是给自己的

那些事我还在做：事故复盘、时间数据、链路图。

但动机变了。以前是想证明这套东西有用，现在是留证据。

布道是给别人的，留证据是给自己的。

这里有个区分，我以前没想清楚：可携带资产有两种。

类型 例子 离开这个场地之后
场内资产 禅道闭环、团队流程改造 蒸发
场外资产 开源插件、专栏、方法论文档 跟着人走

第一种当然要做，它让当下少流血。但它只在你还在位的时候有效。第二种才真正属于自己，因为它署你的名，且不需要任何人批准。

所以如果今年只做一件事，我会把时间戳复盘、链路图、禅道口径，合成一份外人能看懂的文档，署上自己的名字。

不是交给团队。那是报价单。

报价单不需要任何人签字。它只需要在你要谈条件的那一天，是新的。

后记

写完发现，这篇里没有一句是打算发到那个群里的。

它其实是写给我自己的：把“我不布道了”这件事，从一种情绪，变成一个决定。

前几天翻六周前的那一篇（防火的收益是负数：为什么理性人不做长远优化），末尾有一句：“所有靠觉悟维护的资产，最后都死了。”当时写它，是为了劝别人。现在读它，是在劝自己——不要把自己的价值，寄存在别人的觉悟上。

不甘心如果只停在情绪里，十年后还是同一句。每年交一件不需要别人承认的东西，十年后你手上有十件。

到那时候，值不值就不需要谁来评了。

补充 - 关于“能对付一下是一下”

那句话比 BUG 本身更危险。

BUG 是通过率问题；“对付”是资产折旧问题。每对付一次，就把技术债换成信誉债。技术债有账期，可以展期、可以重组；信誉债没有账期，它直接作用在下一次合作上。

toG 的生意半径很小，客户的圈子更小。你今天对付过的那个人，明年可能坐在另一个项目的评审席上。

封面解读

这张封面只压缩一个断言：上面挤得越满，下面流得越细。

那只玻璃漏斗 = 系统本身。 它是全图唯一一件有形状、有硬边的东西，口径是固定的——不是因为谁坏，是因为它就长这样。漏斗不表态，它只是照着瓶颈的形状分配通过量。

漏斗里挤满的那些人形剪影 = 人头。 注意它们的大小、姿态、朝向全都一样，没有一张脸，没有一件衣服的差别。这正是”用人头计量效率”这件事成立的前提——只有当人是可互换的单位时，才会有人觉得多一个就是多一份产能。 它们越挤，越像一堆同质的零件，而不是一群各有判断的人。

卡死在颈部的拥堵 = 瓶颈的真实位置。 压力不在底部，也不在顶部，全部堆在收窄的那一段。所有人都以为问题在上面不够、下面不畅，其实只在中间那一个针孔。

穿过针孔的那一线冷光 = 真正的产出。 它细、恒定、不因为上面多了几十个人而变粗一分。加人改变的是漏斗上方的拥挤程度，不是这一线光的直径。

下方几乎全空的地面 = 加人之后交付没变。 整个下三分之一是空的、暗的、静的，只有托盘里那一小汪光。这是全图最不舒服的地方：上面吵成一片，下面几乎什么都没发生。

画面上方还在往下掉的人 = 下一轮补人已经在路上了。 他们不是被塞进去的，是自己掉下来的——因为”看起来人不够”这个判断，永远能从拥挤里读出来。

没有眼睛，没有嘴，没有指向 = 不进入那个场。 图里没有一张脸朝着读者。谁对谁错不重要，重要的只有一件事：这个口径配多少人，都不会变宽。

一句话总结：漏斗不会因为倒得更猛而变宽——那不是产能不够，那是口径如此。

续补记录（成文过程中新增或改写的观点，供事后回溯）：

一、核心命题——结案的目的就是效率。在 toG 场景里这两件事不是目的与手段的关系，是同一件事。对应第 3 节。

二、判断新增——toG 没有技术难题，只有定位难题：技术栈不深、并发不高、架构不新，所以“做不出来”极少；真正的复杂度在协作面积（四种语言、四方人马）与不可复现（内网、上门、客户数据拿不到）。“疑难”难在指认，不难在解决。对应第 2 节。

三、指标新增——结案时间：从故障发生到指认唯一责任方的时长；并明确与既有 MTTC（需求域反应速度）划清边界。对应第 3 节。

四、概念新增——加人是负优化：结案的本质是排除嫌疑，嫌疑人池随人手同比例扩容；在定位为瓶颈的系统里，加人是往瓶颈上游加压。并给出适用边界——产出为瓶颈时加人线性有效。对应第 4 节。

五、判据新增——归因外移：三种说法落在同一格——把原因挪到够不着的地方，免责的同时免疫于改进；给出可观测判据：看归因落在哪一格。对应第 1 节。

六、修正记录——初稿曾判断“那位产品负责人不在乎效率”，后修正为度量缺失而非需求不存在：他不结案，所以不需要结案工具；组织报表里没有“结案时间”这一栏。并给出动作：三次事故的定位时长，拆出“互相确认不是我”的部分。对应第 5 节。

七、自我修正——停止布道：布道是单向成本，只在对方正在流血时例外；引《孟子·离娄上》“人之患，在好为人师”。对应第 6 节。

八、个人向新增——三句话拆解（市场约束 / 筹码结构 / 动机）；慢筹码；不值是汇率信号不是情绪；两笔账（换到什么 / 付出什么）。对应第 7 节。

九、结论新增——可携带资产两种（场内蒸发 / 场外跟人走）；布道给别人，留证据给自己；报价单不需要签字。对应第 8 节。

十、修订记录（定稿前，2026-11-05）——① 断言限缩：第 2 节原写“toG 没有技术难题”，与第 3 节自建的四语言链路图自相矛盾（一边宣布技术不值钱、一边把最硬的工程当核心资产），改为“没有算法与架构难题”，“技术含量不在写，在指认”改为“价值不在写，在指认”，并补一句说明硬活仍在、只是兑现位置换了。② 时间订正：两处“两年前”均为误记——devops-requirement-before-language 写于 2026-09-18，改为“一个半月前”；devops-negative-return-of-fire-prevention 写于 2026-09-23，改为“六周前”，并为此处裸引补站内链接。③ 射程交代：前言末尾补一段，把“越加人越慢”这个入口明确扩到全文（慢的根源是说不清谁做的；以及走到尽头后一个人还能拿什么交账），使标题与第 6–8 节的重心不再错位。
